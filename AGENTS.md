# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, and any tool that reads `AGENTS.md`) when working with code in this repository.

## What this is

The `ai` CLI — the single control-plane binary for the **AI Development Platform**: reproducible, isolated AI dev environments where workspaces are hardware-isolated **Microsandbox microVMs**. The model path runs agent → host **Headroom** input-compression proxy → **LiteLLM** routing (with always-on **Presidio** secret-masking guardrails on every request) → containerized **Ollama** or a cloud provider; Headroom, Ollama, Presidio, and LiteLLM are all shared host containers (Headroom is no longer installed inside the workspace image). **Caveman** remains the per-project in-workspace output-compression skill. Credentials are **keys-in-LiteLLM**: real provider API keys live in the LiteLLM gateway (env passthrough at launch / its Postgres-backed store), never on platform disk or in the workspace — the agent holds only a scoped LiteLLM **virtual key**. Workspace egress is a **default-deny Microsandbox NetworkPolicy** configured per-project via `ai network` and applied as `msb` net-rules at workspace create; attempted egress is audited by domain name via the `aip-dns` resolver (`ai network log`). Secret/credential masking is LiteLLM's always-on guardrails — Presidio scoped to financial/identity secrets plus the in-process `hide-secrets` detector — which cloud routes cannot bypass. For coding agents the bigger risk is destructive **tool execution**, so an always-on LiteLLM `tool_permission` **tool firewall** denies dangerous command tool-calls (`git push --force`, `rm -rf`, `terraform destroy`, `kubectl delete`, …) at the gateway, alongside an in-process `detect_prompt_injection` callback (the unmaintained LLM Guard was removed). Go 1.26, one static binary, module `github.com/jt-helsinki/ideal-robot`.

**`spec/` is the source of truth, not documentation.** The six numbered specs define the end-state architecture (`01`), delivery slices (`02`), on-disk/repo layout (`03`), the exact CLI surface + JSON envelope + exit codes (`04`), acceptance tests (`05`), and the milestone build plan (`06`). Code comments cite spec sections (e.g. `§17`, `CLI §3.1`, `repo-layout §12.5`) — when changing behavior, read the cited section first and keep code and spec in sync. The build proceeds in milestones **M0–M8** (see `spec/06`), with later work organized as slices **S1–S6** (`spec/02`). The full surface is implemented (M0–M8 plus slices S1, S2, S4–S6; S3 and S7 retired) — host-side **and**, on a provisioned Apple Silicon host, the live external-tool integration: `ai setup` launches the service-tier containers (DNS audit resolver, Ollama, Presidio, LiteLLM + its DB, Headroom); LiteLLM mints scoped agent virtual keys and holds provider keys; workspace microVMs build, boot, and exec; the per-project `ai network` egress policy is applied as Microsandbox net-rules at workspace create; and the DNS egress audit (`ai network log`) works — all verified end-to-end this cycle. The narrow seams that still depend on further bring-up (live service/microVM log capture, verifying the tool-firewall's tool-name/param regexes against the live agent tool schemas, and the nginx-proxy readiness probe) are grep-able (`hardware bring-up`) and tracked in `docs/HARDWARE-BRINGUP.md`. Before changing a slice, read its milestone in `spec/06` and its `[Sx]`-tagged tests in `spec/05`.

## Commands

```bash
make build            # -> bin/ai  (injects version via -ldflags)
make test             # unit tests (go test ./...)
make fmt              # gofmt -w .
make fmt-check        # CI gate: fails if not gofmt-clean
make vet              # go vet
make lint             # golangci-lint (no-op if not installed; CI installs it)
make test-acceptance  # [S1] acceptance suite — STUB; needs Apple Silicon + Docker + Microsandbox
make tidy             # go mod tidy

go test ./internal/setup/ -run TestRunIdempotent   # a single test
go run ./cmd/ai --version --json                   # run without building
```

CI (`.github/workflows/ci.yml`) is split: hosted runners do build/vet/lint/unit-tests; a self-hosted **Apple Silicon** runner runs `[S1]` acceptance (the only host that can run the full stack). Before committing, `make fmt-check vet test build` should all pass — `errcheck` (via golangci-lint) is strict, so explicitly discard intentional writes (`_, _ = fmt.Fprintln(...)`).

## Architecture (the parts that span files)

**Output envelope is the universal contract.** Every command returns the `internal/output` envelope (`{ok, command, data, error, warnings}`, CLI §19). `error.code` **equals** the process exit code (§18: 0 ok, 2 invalid input, 3 missing dependency, 4 runtime failure, 5 permission). Pattern: `Execute()` (in `internal/cli/root.go`) owns an `exitCode` int and an `Emitter`; each cobra command's `RunE` does its work and sets `*exit = emitter.Success(...)` or `emitter.Failure(...)`, returning `nil`. Errors that must carry a specific exit code are `*output.Error` (build with `output.Errorf(code, ...)`); the emitter unwraps them. cobra/arg errors are mapped to exit 2 in `Execute`. Output is **human-readable by default**; the JSON envelope is emitted only with `--json` (commands provide a typed result + a Human renderer — see `ai logs`).

**External tools sit behind injectable interfaces; logic is faked in tests.** Docker/Podman, the Microsandbox runtime (`msb`), Ollama, and LiteLLM are never called directly from orchestration code. Instead: `runtime.Prober`, `setup.Services`, `secrets.Broker`, `litellm.Client`, `ollama.Client`. Orchestrators (`internal/setup`, etc.) take these via a `Deps`-style struct and are unit-tested with fakes; real implementations live in `*_real.go` and are wired by the CLI. Most of these real impls are now wired and verified on Apple Silicon — the service-tier container launches, LiteLLM key minting + provider-credential storage (`litellm.KeyManager`, `secrets.Broker` → LiteLLM `/credentials`), the workspace OCI build + `msb` microVM lifecycle (`workspace.Builder`/`Sandbox` — `Exec` one-shot/buffered, `ExecInteractive` a real PTY via `msb exec -t -u workspace` backing `ai shell` + the TUI `e` key), and the `ai network` egress policy applied as `msb` net-rules. **Workspace sessions are tmux-transparent:** every shell + agent CLI runs in a persistent, reattachable per-name **tmux session** inside the microVM (`tmux new-session -A`, all as the `workspace` user via `ExecInteractive`), with a managed `~/.tmux.conf` (`agentcfg.TmuxConfig`, mouse-scroll on / status bar off) written at workspace start so the user never types a tmux command — surfaced by `ai agent <cli> [name]` (per-CLI session), `ai attach [session] [name]`, `ai sessions [name]` (and the TUI Sessions view); `Manager.Shell/Agent/Attach/ListSessions/KillSession`. **The few genuinely-unwired seams are commented `hardware bring-up`** (live service/microVM log capture, verifying the tool-firewall's tool-name/param regexes against the live agent tool schemas, and the nginx-proxy readiness probe). **Do not invent the external tools' CLI/API invocations** — verify against the real tool's docs (msb/CoreDNS/Presidio commands and the LiteLLM/Ollama HTTP APIs were verified empirically) or leave the seam and mark it deferred.

**Newer packages worth knowing.** `internal/ollama` (required local-model service, run as the `aip-ollama` container), `internal/contextopt` (Headroom strategy + Caveman level, per-project, surfaced by `ai context`; the strategy maps to Headroom's per-request `keep_turns`/`output_buffer_tokens` body knobs baked into the agent's `extra_body` at workspace start — `HeadroomParams`), `internal/overlay` (S4 per-workspace persistence), `internal/envimage` (workspace OCI image build from the project Dockerfile), `internal/console` (admin-dashboard URL registry for `ai services console`), `internal/templates` (embedded OS/stack/agent-CLI snippets), `internal/uninstall` (native `ai uninstall` teardown), `internal/egress` (per-project workspace egress policy — mode + allow-list + published ports, surfaced by `ai network`; `MsbNetworkArgs` renders it into `msb` net-rules), `internal/agentcfg` (the in-VM agent provider config written at workspace start — base_url → host Headroom `:18787`, the scoped virtual key, and the project's `HeadroomParams` as request `extra_body`; the in-VM agent model picker is the UNION of the named aliases + the INSTALLED Ollama models (rendered `ollama/<name>`, listed via the injected `workspace.ModelLister`/`ollama.RealClient()`, skipped if Ollama is down — never fails the start) + a maintainer-curated cloud seed `internal/agentcfg/cloud_models.yaml` (`agentcfg.CloudModels()`, an easy-to-edit `<provider>/<model-id>` list across openai/anthropic/gemini/groq; LiteLLM's wildcards route whatever's named, so editing this file adds/removes picker suggestions with no code change), built by `Manager.pickerModels` at workspace start; `agentcfg.RefreshScript` also generates a self-contained in-VM `refresh-models` command — installed at `/usr/local/bin/refresh-models` at start (staged via `Sandbox.WriteFile`, moved into place with `sudo install -m 0755`) — that re-pulls the picker WITHOUT restarting the microVM: it `curl`s the gateway's auth-free `/ollama/api/tags` route, merges the live local models with the baked static set (aliases ∪ cloud seed), and rewrites the two configs BYTE-IDENTICAL to a fresh start (parity pinned by executing the generated script against a fake `curl` in tests; live in-VM execution is a `hardware bring-up` item)), `internal/litellm` (also the `KeyManager` virtual-key client), `internal/layout`, and `internal/tui` (the K9s-style `ai ui` management TUI — parent package + sub-packages `scope` [startup project/scope resolution + create-target validation], `views` [one bubbletea model per screen: services/projects/project/network/context/models/secrets/create], with the parent owning the alt-screen shell, the `:` menu, the create overlay, and the `tea.ExecProcess` flows; views take injected funcs over the existing package APIs and honour `ai theme`). The `aip-dns` CoreDNS resolver is the egress-audit backend (`ai network log`): microVMs boot with `--dns-nameserver` pointed at it, so every queried name is logged. **Version control is out of scope** — there is no git package and `ai create` runs no git. **Supported hosts are macOS (Apple Silicon) and Linux** — there is no cross-OS path-translation layer.

**State is split global vs project-local, written atomically.** Global lives under `~/.ai-platform/` (config, `runtime.yaml`, `versions.yaml`, `projects.yaml` index); per-project state lives in `<project>/.ai-platform/` (tracked `Dockerfile`/`config.yaml`/`profile.yaml`/`project.yaml`/`skills/caveman/`, gitignored `run/`). All paths derive from `os.UserHomeDir()` via `internal/paths`, so **tests redirect with `t.Setenv("HOME", t.TempDir())`**. All state/config writes go through `internal/conffile` (atomic YAML — temp file + `rename`; reads reject unknown fields via `KnownFields`). `versions.yaml` (`internal/versions`) is the **source of truth for the service-tier image refs** — pinned by **image + tag** (default `latest`; no digests — they are platform/arch specific) — and `internal/setup`'s `containerImage` resolves every service image from it, falling back to `versions.Default()` when the file is absent or an entry is incomplete. The `--json` output envelope (`internal/output`) and the in-workspace agent-CLI configs (`opencode.json`, `~/.pi/agent/models.json`) stay JSON. Config merges `project > global` via `internal/config` (deep map-merge).

**Dual runtime model.** Microsandbox microVMs run workspaces; Docker/Podman run the service tier on the shared `aip-net` network, reconciled in order network → DNS → Ollama → Presidio → LiteLLM(+DB) → Headroom → Open WebUI/Odysseus (if enabled) → nginx proxy (LAST). **`aip-proxy` (nginx) is the SOLE host entry point to the service tier: every other service container is INTERNAL-ONLY on `aip-net` (reached by name) — only nginx publishes ports to the host** (besides the loopback-only `aip-litellm-db` :5442 and `aip-dns` :15353). The services: `aip-dns` (CoreDNS egress-audit resolver, bound to host loopback `127.0.0.1:15353/udp`; microVMs use it via `--dns-nameserver`), `aip-ollama` (required local models, INTERNAL-ONLY — no host publish — reached by name at `http://aip-ollama:11434` and from the host via nginx's `/ollama` route; models persist on the host at `~/.ai-platform/models`), the `aip-presidio-analyzer`/`aip-presidio-anonymizer` pair backing LiteLLM's always-on secret-masking guardrail, `aip-litellm` (the gateway, INTERNAL-ONLY — no host publish — reached by name at `aip-litellm:4000` by Headroom and by nginx's `/llm` route) plus a small `aip-litellm-db` Postgres (trust auth, host port 5442 loopback) that backs LiteLLM's DB-backed admin UI/virtual keys + the encrypted provider-credential store (the one stateful service-tier piece), `aip-headroom` (the input-compression proxy in front of LiteLLM, `OPENAI_TARGET_API_URL=http://aip-litellm:4000`, `HEADROOM_NO_CCR_INJECT_TOOL=1`; pulled image, never built — INTERNAL-ONLY on :8787 behind nginx, no host publish), `aip-proxy` (the `nginx:1.27-alpine` reverse proxy, the SOLE host ENTRY: on host :18787 it fronts the model path `location /v1` → `aip-headroom:8787` [the agent chat path, PRESERVED unchanged], the LiteLLM admin surface `location /llm` → `aip-litellm:4000` [prefix stripped: `/model/info`, `/v1/models`, `/health*`, `/key*`, `/credentials`], and the Ollama API `location /ollama` → `aip-ollama:11434` [prefix stripped] — specific prefixes before the catch-all `/` [the DEFAULT route, also → Headroom]; the model path `/`+`/v1` ride Headroom, while `/llm`/`/ollama` and the UI vhosts BYPASS it; the web UIs are now **Host-based VHOSTS on the SAME :18787** — `litellm.<domain>` → `aip-litellm:4000` [admin UI at `/ui`; always, litellm is core], `chat.<domain>` → `aip-open-webui:8080`, `odysseus.<domain>` → `aip-odysseus:7000` [each with WebSocket upgrade headers], rendered only when enabled — NOT separate host ports; SSE-friendly — buffering off, long timeouts; the per-vhost HTTPS termination point later, binds 0.0.0.0:18787 in server mode; reconciled LAST so its upstreams incl. the enabled UIs are up first — nginx resolves a literal `proxy_pass` host at config-load. The `<domain>` is the resolved platform base domain (`runtime.yaml` `domain`, default `aip.local`, threaded through `ensureProxy`/`ensureOpenWebUI`/`ensureOdysseus` via `reconcileDomain()`); **standalone** `ai setup` writes an `/etc/hosts` managed block (consent + sudo via `uihosts.SyncHosts`, else a printed manual block) pointing **all** UI subdomains [incl. not-yet-enabled ones, so enabling them later needs no re-edit] at `127.0.0.1`, **server** prints the DNS (`*.<domain>` → server) + TLS-at-nginx operator contract (`uihosts.ServerGuidance`, no `/etc/hosts` edit), both surfaced in `ai doctor` too; the UI→subdomain map is declared ONCE in `internal/services` (`Service.UISubdomain`/`UIVhosts`) and consumed by `internal/uihosts` (+ setup/doctor/uninstall, which removes the standalone hosts block on teardown). The live UI-vhost routing, the sudo `/etc/hosts` write (`hostsfile.Plan` → temp file → `sudo cp`), and the Open WebUI/Odysseus reverse-proxy envs are `hardware bring-up`. The optional `aip-open-webui` (the chat UI, INTERNAL-ONLY — nginx serves it as `chat.<domain>:18787` — routed through the nginx gateway → Headroom → LiteLLM via `OPENAI_API_BASE_URL=http://aip-proxy/v1`, the same path workspace agents + Odysseus use, never direct to LiteLLM — with `ENABLE_OLLAMA_API=false`/`WEBUI_AUTH=false` + `WEBUI_URL`/`CORS_ALLOW_ORIGIN`=its chat-vhost URL; the LiteLLM master key, when set, is passed via env passthrough as `OPENAI_API_KEY`) and the optional **Odysseus** AI workspace (`ai setup --optional odysseus`, OFF by default): ONE optional service named `odysseus` owning FOUR INTERNAL-ONLY containers — `aip-odysseus` (the app, nginx serves it as `odysseus.<domain>:18787`, image `ghcr.io/pewdiepie-archdaemon/odysseus:latest`, with best-effort `APP_BIND=0.0.0.0`/`APP_PUBLIC_URL`/`SECURE_COOKIES=false` reverse-proxy seeds — env names unconfirmed, bring-up) plus the companions `aip-chromadb`/`aip-searxng`/`aip-ntfy` (reached by name on `aip-net`, no host publish — nginx is the sole publisher). It routes models through the nginx gateway → Headroom → LiteLLM (`OLLAMA_BASE_URL=http://aip-proxy/v1`, reusing the LiteLLM master key via env passthrough as `OPENAI_API_KEY`). The host CLI reaches LiteLLM (admin via `localhost:18787/llm`, the chat test via `localhost:18787/v1` to exercise the real Headroom→LiteLLM model path) and Ollama (via `localhost:18787/ollama`) through nginx, never a container directly (`litellm.AdminBaseURL`/`GatewayBaseURL`, `ollama.DefaultBaseURL`); the agent microVM `/v1` path (`host.microsandbox.internal:18787/v1` → Headroom) is preserved unchanged. Live end-to-end routing through these nginx routes is a `hardware bring-up` item. **It MOUNTS THE HOST DOCKER SOCKET** (`/var/run/docker.sock`, the maintainer's explicit requirement) — full host-Docker control, an elevated privilege outside the sandbox — so it is opt-in and carries a sharpened security warning. Its providers are configured in-app (`/setup`); the env values are best-effort seeds (hardware bring-up). `ai uninstall` removes its `aip-*` containers + volumes by the existing wildcard. There is no native firewall service; provider credentials live in LiteLLM (keys-in-LiteLLM). Detection (`internal/runtime` + `internal/sandbox`) is parameterized by `GOOS/GOARCH` + a `Prober` so it tests on any host; missing deps → exit 3, missing rootless/virtualization → exit 4. macOS requires **Apple Silicon** (no Intel). **Deployment roles** (chosen interactively by `ai setup`, or `--mode`, persisted as `role:` in `runtime.yaml`): **standalone** (default — full service tier + workspaces here; shared services bind **127.0.0.1**), **server** (only the service tier, bound **0.0.0.0** for remote clients, no workspaces — preflight needs only docker + rootless), **client** (only workspaces; routes to a remote `--server` address held in `ai_platform_host`, skips the local reconcile — preflight needs only msb + virtualization). The role drives `blockingPrereqsForRole` and the `bindHost` threaded through `Services.Reconcile`/`ensure*` (Postgres + DNS stay loopback regardless); since the service containers are now internal-only, `bindHost` governs only what **nginx (`ensureProxy`)** publishes (the sole host entry — `litellmRunArgs`/`ensureOllama`/`ensureOpenWebUI`/`ensureOdysseus` no longer publish), and `RelaunchLiteLLMWithAuth` still derives its bind from the persisted role via `currentBindHost()` for the proxy. Per-project workspace egress is declared via `ai network` (modes deny[default]/public/unrestricted, allowed host services incl. domains + `*.suffix`, published ports, stored in `config.yaml`) and applied as default-deny Microsandbox net-rules (`egress.MsbNetworkArgs`) at workspace create. **Model gateway wiring** (`ai gateway show|set|clear`, `internal/cli/gateway.go`): the machine-wide `ai_platform_host` in `runtime.yaml` (set by `ai gateway set <host[:port]>` or `ai setup --mode client --server`) selects which gateway every workspace microVM on this host routes through. `internal/workspace` derives it at start via `runtime.ResolveGateway(Info.HostAddress())` — bare host or `host:port`, default port 18787; empty → `host.microsandbox.internal:18787` (standalone/local) — and uses the resolved `http://<host>:<port>/v1` for the agent provider configs' `base_url` and the resolved `<host>:<port>` for `MsbNetworkArgs(network, gatewayHost, gatewayPort)`'s always-on egress allow rule. `ai gateway` exits 3 (no runtime.yaml — run `ai setup`), 2 (invalid address), 4 (persist/read failure). **Platform base domain** (`ai domain [name]`, `internal/cli/domain.go`): the machine-wide `domain` field in `runtime.yaml` is the base domain the nginx UI subdomains hang off — `litellm.<domain>`, `chat.<domain>`, `odysseus.<domain>` — defaulting to `aip.local` (`runtime.DefaultDomain`, resolved via `Info.ResolveDomain()`/`runtime.ResolveDomain`) for local/standalone and overridden in server mode. `ai domain` with no arg SHOWS the resolved domain; with a name it VALIDATES a lowercase DNS hostname (labels of `[a-z0-9-]`, no scheme/path/whitespace, no leading/trailing dot) and persists it, mirroring `ai gateway`'s load-modify-save + exit codes (3 no runtime.yaml, 2 invalid, 4 persist/read). This `domain` is wired into the nginx UI vhosts + the standalone `/etc/hosts` block (see the Dual runtime model above).

**Model catalogue is global and agent-selected.** LiteLLM (the shared host gateway) exposes models via per-provider **wildcards** (`ollama/*`, `openai/*`, `anthropic/*`, `gemini/*`, `groq/*`) plus a few named handles (aliases `gpt-5.5`/`claude-opus`/`gemini-pro`); the default model is the local Ollama `gemma4` (→ `ollama/gemma4:31b`, `litellm.DefaultRouting` in `internal/litellm`). The in-workspace agent names any model per request and LiteLLM routes it (real provider keys live in LiteLLM; the agent authenticates to the gateway with a scoped virtual key, Ollama needs none) — there is **no per-project model config**. LiteLLM's generated config renders **always-on guardrails** (all `default_on: true`), scoped to **secrets/credentials, not general PII**: `presidio-secrets-input` (pre_call) + `presidio-secrets-output` (post_call) mask only financial/identity secrets (CREDIT_CARD, US_SSN, US_BANK_NUMBER, IBAN_CODE, CRYPTO — see `secretEntities`), plus `hide-secrets` (LiteLLM's in-process detect-secrets) for API keys/tokens. Masking general PII (names, places, emails) was deliberately removed — it corrupted ordinary coding prompts. Additionally, an in-process **prompt-injection** detector (`litellm_settings.callbacks: ["detect_prompt_injection"]`, local heuristic, no external service) and a **tool firewall** (`guardrail: tool_permission`, `mode: post_call`) that DENIES destructive command tool-calls (`git push --force`, `rm -rf`, `terraform destroy`, `kubectl delete`, … — `destructiveCommandPatterns` in `internal/litellm`) — for coding agents the bigger risk is destructive tool execution, not prompt content. The unmaintained **LLM Guard was removed**; Guardrails AI (needs a Hub token + per-guard install) remains **deliberately deferred**. Because default-on guardrails run on every request and all routes (cloud included) traverse the proxy, cloud calls cannot bypass them. Registering a model ≠ installing it (an Ollama model still needs `ollama pull`; a cloud model still needs its key). `ai services start|stop|restart` manage the whole platform container set (ollama, presidio, litellm, headroom, proxy, open-webui, odysseus [→ its four containers], dns); `ai services update [service]` (and the TUI Services pane's `p` key) force-RE-PULLS the latest images (`Services.UpdateImages` — unlike the first-run `PullImages` it does NOT skip already-present images, so a moved `latest` tag is refreshed) then restarts the target so its container is recreated against the new image (`setup.UpdateService`); ClawPatrol is gone and there is no native service to manage. The LiteLLM admin UI is secured with `UI_USERNAME`/`UI_PASSWORD`/`LITELLM_MASTER_KEY` passed by **env passthrough** (values never in argv/config/disk); `ai setup` prompts for the password on a TTY.

**The CLI surface is FLAT: workspace management lives in top-level verbs** (CLI §3/§4) — `ai create`/`ai list`/`ai delete` (create/list/delete a workspace) and `ai start`/`ai stop`/`ai restart`/`ai destroy`/`ai exec`/`ai shell`/`ai agent`/`ai attach`/`ai sessions` (microVM lifecycle + sessions), each taking an OPTIONAL `[name]` resolved via `resolveProjectName` (explicit name → `--project` → cwd workspace). The grouped `ai workspace …` / `ai project …` commands were **removed** — the flat verbs are the only surface (their shared RunE bodies live in `internal/cli/workspace.go` as `workspace*RunE`, plus the `newCreateCmd`/`newListCmd`/`newDeleteCmd` constructors in `project.go`; the envelope `command` keys stay `workspace.*`/`project.*`). The user-facing noun is **"workspace"** in all help/messages/TUI labels, but internal package/type/field names (`internal/project`, `project.Entry`, `state.Project`, `views.Projects`/`ProjectsHub`) and JSON data keys (`{"project": …}`) keep "project" for stability. NB: `ai doctor [name]` is **consolidated** — it always reports platform health + every service-tier service (incl odysseus + companions), and ADDITIONALLY the workspace-runtime checks (rootless + virtualization) when inside a workspace dir (cwd/ancestor) or given `[name]`; there is no separate `ai workspace doctor`. It always exits 0 with a report (per-check status conveys health).

**`ai create` is an in-process `charmbracelet/huh` wizard** (CLI §3.1): workspace name, OS (`debian-trixie`/`debian-bookworm`/`ubuntu`/`alma`), agent CLIs (multi-select: `opencode`/`pi`/`claude-code`/`codex`/`gemini` — `opencode` (default tool) and `pi` are installed by default, both wired to LiteLLM), default agent CLI, and software stacks (`go`/`node`/`python`/`rust`/`java`/`maven`/`deno`) are picked across the wizard's five groups. Every input also has a flag (`--name`/`--os`/`--agents`/`--stacks`); on a TTY the flags **pre-seed** the wizard (which always shows — flags are never required there), while under `--json` or no TTY the spec is built straight from the flags with no prompt and `--os` is **required** (a missing `--os` exits 2). The workspace is created **in the current directory** (no fixed `~/projects`); if the cwd is already a workspace it **attaches** instead. The platform runs **no git** (VCS is out of scope). `--dry-run` emits the side-effect-free action plan. The command itself uses no PTY; automation drives it through a pseudo-terminal (`creack/pty`) only via the acceptance harness in `test/acceptance` (§1.4).

## Conventions

- **Commands prompt on a TTY** (CLI §1.8), via the shared helpers in `internal/cli/prompt.go` (`interactive`/`runForm`/`promptText`/`promptSecret`/`promptChoice`/`promptMultiChoice`, all built on `charmbracelet/huh`). On a terminal the prompt ALWAYS shows, **pre-seeded** with any value given as an arg/flag (the user confirms/edits — the value never silently bypasses the TUI); only under `--json`/no-TTY is a provided value used directly, with a missing required value erroring (exit 2) so automation stays scriptable. Two exceptions: a **hidden credential value** (`ai secrets set --value/--stdin`) is used directly even on a TTY (a hidden field can't show a seed), and `ai services start|stop|restart` act directly on an explicit name/`all` and only show the checkbox with no arg. Known option sets are shown as selects/checkboxes. **All of a command's prompts must share ONE `runForm`** so the user can navigate back between them — never chain separate prompt calls. The TUI look-and-feel is **theme-selectable**: `internal/ui` owns a registry of named themes (huh built-ins `default`/`dracula`/`catppuccin`/`base16`/`monochrome` plus custom palettes in `custom_themes.go` — `orange`/`synthwave`/`cyberpunk`/`tokyo-night`/`nord`/`gruvbox`/`onedark`/…, each wrapping a huh theme + heading accent; `ui.TableStyles()` themes the `ai ui` tables with the active accent), persisted per host in `~/.ai-platform/config/ui.yaml` and applied once at startup (root `PersistentPreRun` → `ui.Apply(ui.LoadThemeName())`); `ai theme [name]` shows/selects it (the semantic status colours stay fixed across themes).
- **No single-character variable names anywhere** — including method receivers and loop vars (`store`, `emitter`, `prober`, `entry`, `value`, …). Self-documenting names over Go's terse-receiver convention. The one kept exception is the test handle `t *testing.T`.
- **Secrets never touch platform disk.** Values flow straight to the LiteLLM credential store via `secrets.Broker` (`internal/secrets`, which `ai secrets` fronts); `secrets.Entry` has no value field by design, so listings can't leak.
- **Parallelize with subagents + git worktrees where the work is disjoint — but never at the cost of merge chaos.** When a task decomposes into independent units that touch *different* files, prefer launching multiple subagents in parallel, each in its own git worktree (`isolation: worktree`), then integrate by pulling each branch's files (`git checkout <branch> -- <files>`). Do NOT parallelize units that edit the **same** file (notably `internal/setup/setup_real.go`, `internal/tui/tui.go`) — sequence those instead. The rule that keeps integration clean: each agent owns a **disjoint file set**, and the parent does any shared wiring (e.g. registering new views in `tui.go`) itself. If you can't partition the work into disjoint file sets, do it single-threaded.
- Commit messages must not include AI-attribution trailers (no `Co-Authored-By` for the assistant). Commit only when asked; the work lives on a feature branch off `main`.
