# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, and any tool that reads `AGENTS.md`) when working with code in this repository.

## What this is

The `ai` CLI — the single control-plane binary for the **AI Development Platform**: reproducible, isolated AI dev environments where workspaces are hardware-isolated **Microsandbox microVMs**. The model path runs agent → host **Headroom** input-compression proxy → **LiteLLM** routing (with always-on **Presidio** secret-masking guardrails on every request) → containerized **Ollama** or a cloud provider; Headroom, Ollama, Presidio, and LiteLLM are all shared host containers (Headroom is no longer installed inside the workspace image). **Caveman** remains the per-project in-workspace output-compression skill. Credentials are **keys-in-LiteLLM**: real provider API keys are added via `ai keys` and live ENCRYPTED in the LiteLLM gateway's Postgres credential store (encrypted at rest by `LITELLM_SALT_KEY`), never on platform disk, in `config.yaml`, or in the workspace — the agent holds only a scoped LiteLLM **virtual key**. The served model set is catalog-driven (models.dev) and DB-backed: adding/removing a provider key syncs that provider's models in/out of LiteLLM's DB, so there is no `model_list`/wildcards/named aliases in the rendered config. Workspace egress is a per-project Microsandbox NetworkPolicy configured via `ai network` and applied as `msb` net-rules at workspace create; the **default mode is now `public`** (allow-outbound — private ranges still blocked; lets the in-VM container runtime pull images and AI processes reach the internet), with `deny`/`unrestricted` as the re-lockable alternatives; attempted egress is audited by domain name via the `aip-dns` resolver (`ai network log`). Every workspace microVM also ships a **rootful in-VM OCI container runtime** (containerd + nerdctl + runc + CNI, from the pinned `nerdctl-full` tarball in every OS base Dockerfile), started best-effort at workspace start. Secret/credential masking is LiteLLM's always-on guardrails — Presidio scoped to financial/identity secrets plus the in-process `hide-secrets` detector — which cloud routes cannot bypass. For coding agents the bigger risk is destructive **tool execution**, so an always-on LiteLLM `tool_permission` **tool firewall** denies dangerous command tool-calls (`git push --force`, `rm -rf`, `terraform destroy`, `kubectl delete`, …) at the gateway. (The in-process `detect_prompt_injection` callback AND the unmaintained LLM Guard were both removed — crude heuristics that false-positived on ordinary coding/Ollama traffic, rejecting it with "Rejected message. This is a prompt injection attack.") Go 1.26, one static binary, module `github.com/jt-helsinki/ideal-robot`.

**`spec/` is the source of truth, not documentation.** The six numbered specs define the end-state architecture (`01`), delivery slices (`02`), on-disk/repo layout (`03`), the exact CLI surface + JSON envelope + exit codes (`04`), acceptance tests (`05`), and the milestone build plan (`06`). Code comments cite spec sections (e.g. `§17`, `CLI §3.1`, `repo-layout §12.5`) — when changing behavior, read the cited section first and keep code and spec in sync. The build proceeds in milestones **M0–M8** (see `spec/06`), with later work organized as slices **S1–S6** (`spec/02`). The full surface is implemented (M0–M8 plus slices S1, S2, S4–S6; S3 and S7 retired) — host-side **and**, on a provisioned Apple Silicon host, the live external-tool integration: `ai setup` launches the service-tier containers (DNS audit resolver, Ollama, Presidio, LiteLLM + its DB, Headroom); LiteLLM mints scoped agent virtual keys and holds provider keys; workspace microVMs build, boot, and exec; the per-project `ai network` egress policy is applied as Microsandbox net-rules at workspace create; and the DNS egress audit (`ai network log`) works — all verified end-to-end this cycle. The narrow seams that still depend on further bring-up (live microVM (`msb`) log follow, live `nerdctl run`/`pull` in the workspace, and live end-to-end confirmation of the tool-firewall + nginx routes against the running stack) are grep-able (`hardware bring-up`) and tracked in `docs/HARDWARE-BRINGUP.md`. Before changing a slice, read its milestone in `spec/06` and its `[Sx]`-tagged tests in `spec/05`.

CI (`.github/workflows/ci.yml`) is split: hosted runners do build/vet/lint/unit-tests; a self-hosted **Apple Silicon** runner runs `[S1]` acceptance (the only host that can run the full stack). Before committing, run **`make check`** (= `fmt-check vet lint test build`) — it must all pass. `errcheck` + the rest of golangci-lint are strict, so explicitly discard intentional writes (`_, _ = fmt.Fprintln(...)`) and keep `make lint` clean.

## Architecture (the parts that span files)

**Output envelope is the universal contract.** Every command returns the `internal/output` envelope (`{ok, command, data, error, warnings}`, CLI §19). `error.code` **equals** the process exit code (§18: 0 ok, 2 invalid input, 3 missing dependency, 4 runtime failure, 5 permission). Pattern: `Execute()` (in `internal/cli/root.go`) owns an `exitCode` int and an `Emitter`; each cobra command's `RunE` does its work and sets `*exit = emitter.Success(...)` or `emitter.Failure(...)`, returning `nil`. Errors that must carry a specific exit code are `*output.Error` (build with `output.Errorf(code, ...)`); the emitter unwraps them. cobra/arg errors are mapped to exit 2 in `Execute`. Output is **human-readable by default**; the JSON envelope is emitted only with `--json` (commands provide a typed result + a Human renderer — see `ai logs`).

**External tools sit behind injectable interfaces; logic is faked in tests.** Docker/Podman, the Microsandbox runtime (`msb`), Ollama, and LiteLLM are never called directly from orchestration code. Instead: `runtime.Prober`, `setup.Services`, `litellm.KeyManager`, `litellm.Client`, `ollama.Client`. Orchestrators (`internal/setup`, etc.) take these via a `Deps`-style struct and are unit-tested with fakes; real implementations live in `*_real.go` and are wired by the CLI. Most of these real impls are now wired and verified on Apple Silicon — the service-tier container launches, LiteLLM key minting + provider-credential storage (`litellm.KeyManager` → LiteLLM `/credentials`, encrypted at rest, fronted by `ai keys`), the workspace OCI build + `msb` microVM lifecycle (`workspace.Builder`/`Sandbox` — `Exec` one-shot/buffered as `workspace`, `ExecRoot` one-shot as image ROOT via `msb exec -u root` [msb's no-`-u` default is the unprivileged `workspace` user (uid 1000), NOT root; used to boot the rootful in-VM containerd], `ExecInteractive` a real PTY via `msb exec -t -u workspace` backing `ai shell` + the TUI **Shell** tab's `enter`/`a` attach via `tea.ExecProcess`), and the `ai network` egress policy applied as `msb` net-rules. Every workspace VM now ships a rootful in-VM OCI runtime (containerd + nerdctl + runc + CNI from the pinned `nerdctl-full` tarball in each OS Dockerfile); `Manager.Start` brings containerd up best-effort via `ensureContainerd` (probe `nerdctl info` quietly — `sh -c 'timeout 5 nerdctl info >/dev/null 2>&1'`; else boot `setsid containerd &` then POLL `nerdctl info` for TRUE readiness (the daemon serving requests, NOT merely the socket file existing) so the daemon both establishes and serves before the exec returns — msb tears down the exec's process group on return, which would otherwise kill the just-forked daemon; verified live on Apple Silicon). **Workspace sessions are tmux-transparent:** every shell + agent CLI runs in a persistent, reattachable per-name **tmux session** inside the microVM (created DETACHED via a returning `ExecContext` — `tmux new-session -d` — so the tmux server daemonizes and the session PERSISTS independent of any client, then attached with `tmux attach-session` via `ExecInteractive`; all as the `workspace` user. Creating the session inside the interactive attach instead tied its life to that one PTY, so it vanished from `ai sessions` once the client went away), with a managed `~/.tmux.conf` (`agentcfg.TmuxConfig`, mouse-scroll on / status bar off) written at workspace start so the user never types a tmux command — surfaced by `ai agent <cli> [name]` (per-CLI session), `ai shell [name]` (on a TTY: a picker to ATTACH an existing session or CREATE a new named one — default new name `shell`; `--session <s>` skips the picker), `ai attach [session] [name]` (attaches an EXISTING session — explicit `[session]` attaches directly, else it lists them to pick; with NO sessions it prints a hint pointing at `ai shell`, never creates), `ai sessions [name]` + `ai sessions kill <session> [name]` (and the TUI **Shell** sub-tab); `Manager.Shell/Agent/Attach/ListSessions/KillSession`. The VM is **headless**: the agent's PTY byte stream is rendered by the user's **host** terminal emulator (WezTerm/Ghostty/iTerm — a modern one is recommended for OpenCode), so correct rendering of modern TUI CLIs is a terminfo + tmux-config problem, not a VM-side emulator. Each base image ships `ncurses-term` (the `tmux-256color` terminfo entry) and `TmuxConfig` sets `default-terminal "tmux-256color"` + `terminal-features ",*:RGB"` (24-bit truecolor) + `",*:extkeys"`/`extended-keys on` (CSI-u extended keys, so OpenCode's shift+enter / ctrl-combos survive tmux), requiring tmux ≥ 3.2 (all four bases qualify). Known limitation: tmux does **not** pass GPU/graphics protocols (kitty graphics, sixel) through, so a TUI's image rendering won't work inside the session. **The few genuinely-unwired seams are commented `hardware bring-up`** (live microVM (`msb`) log follow, live `nerdctl run`/`pull` in the workspace, and live end-to-end confirmation of the tool-firewall + nginx routes against the running stack). **Do not invent the external tools' CLI/API invocations** — verify against the real tool's docs (msb/CoreDNS/Presidio commands and the LiteLLM/Ollama HTTP APIs were verified empirically) or leave the seam and mark it deferred.

**Newer packages worth knowing.** `internal/ollama` (required local-model service, run as the `aip-ollama` container), `internal/contextopt` (Headroom strategy + Caveman level, per-project, surfaced by `ai context`; the strategy maps to Headroom's per-request `keep_turns`/`output_buffer_tokens` body knobs baked into the agent's `extra_body` at workspace start — `HeadroomParams`), `internal/overlay` (S4 per-workspace persistence), `internal/envimage` (workspace OCI image build from the project Dockerfile), `internal/console` (admin-dashboard URL registry for `ai services console`), `internal/templates` (embedded OS/stack/agent-CLI snippets), `internal/uninstall` (native `ai uninstall` teardown), `internal/egress` (per-project workspace egress policy — mode + allow-list + published ports, surfaced by `ai network`; `MsbNetworkArgs` renders it into `msb` net-rules), `internal/agentcfg` (the in-VM agent provider config (re)loaded into the microVM on EVERY workspace start/restart by `workspace.registerAgentProviders` — base_url → host Headroom `:18787`, the scoped virtual key, and the project's `HeadroomParams` as opencode request body knobs. **ALL FIVE agent CLIs route through the gateway by default**: opencode (`~/.config/opencode/opencode.json`) + pi (`~/.pi/agent/models.json`) via a JSON config file; claude-code/codex/gemini via ENV VARS written into the in-VM agent env file `~/.config/aip/agent-env.sh` (`AgentEnvScript`: `ANTHROPIC_BASE_URL`+`ANTHROPIC_AUTH_TOKEN` for claude-code at the gateway ROOT (no /v1, it appends /v1/messages); `GOOGLE_GEMINI_BASE_URL`+`GEMINI_API_KEY` for gemini at the root; codex via a KEYLESS `~/.codex/config.toml` `[model_providers.aip-gateway]` block — `base_url=<gateway>/v1`, `wire_api="responses"` (codex requires the Responses API, which LiteLLM exposes), `env_key="AIP_GATEWAY_KEY"`). The agent env file is sourced by every session — the agent-launch command wraps each CLI in `bash -lc 'source <env>; exec <cli>'` (`wrapWithAgentEnv`) and a managed `~/.bash_profile` (`agentcfg.BashProfile`) sources it for interactive `ai shell`/`ai attach`. **HARD SECURITY INVARIANT: the scoped virtual key (and any real key) is NEVER written to host disk** — the host-side, USER-EDITABLE templates under `<project>/.ai-platform/agents/` (`opencode.json`/`pi.json`/`codex.toml`, scaffolded KEYLESS at `ai create` by `project.writeAgentTemplates`, repo-layout §12.1c) are KEYLESS (base_url is not a secret); the key is injected ONLY into the final config/env written INTO the VM via `Sandbox.WriteFile`. At start the platform READS each host template, DEEP-MERGES (`MergeOpenCodeConfig`/`MergePiConfig` — generated dynamic provider block WINS, user's other keys survive) the dynamic values, and writes the final config in-VM; user edits survive restart (a present template is merged, never clobbered with the key-bearing form; only an ABSENT template is re-scaffolded keyless via `ensureAgentTemplates`). A test asserts the host templates contain no key. The in-VM agent model picker is EXACTLY the models the LiteLLM gateway currently SERVES (its live DB-backed models), sourced via the injected `workspace.ServedModels` (wired to `litellm.KeyManager.ListModels`) and built by `Manager.pickerModels` at workspace start — the served names are sorted, the list DEGRADES GRACEFULLY to EMPTY when the gateway is unreachable (never fails the start), and NO default model is written into the agent configs; `agentcfg.RefreshScript` also generates a self-contained in-VM `refresh-models` command — installed at `/usr/local/bin/refresh-models` at start (staged via `Sandbox.WriteFile`, moved into place with `sudo install -m 0755`) — that re-fetches the picker WITHOUT restarting the microVM: it `curl`s the gateway's `/v1/models` endpoint (authenticated with the scoped virtual key) and rewrites the opencode+pi configs BYTE-IDENTICAL to a fresh start's CANONICAL (non-template-merged) config from the served list (host-template edits + the env-routed CLIs re-apply on the next start); on fetch failure it leaves the configs UNTOUCHED and exits non-zero (it no longer bakes any static model set), parity pinned by executing the generated script against a fake `curl` in tests; live in-VM execution is a `hardware bring-up` item), `internal/apps` (the opt-in **in-VM AI apps** that run as `nerdctl`/containerd containers INSIDE the workspace microVM — Open WebUI + AnythingLLM; a declarative `Manifest` per app [image+tag pin, container port, persisted data dir, optional `/workspace` mount, gateway-pointing env], a per-`(workspace,app)` UNIQUE host-port allocation [reserved machine-wide across all workspaces' configs, persisted in the project `config.yaml` `apps:` block, published ONLY while installed], and a lifecycle `Manager` over an injected in-VM `ExecRunner` [install/remove/update/start/stop/restart/list]; surfaced by `ai apps` + a per-workspace TUI **Apps** view + the `ai create --apps` multi-select. Each app routes through the SAME gateway the agents use with the workspace's scoped virtual key; data persists at `/persist/apps/<key>` on the overlay; ports use the existing `egress.MsbNetworkArgs` publish plumbing [`host:<port> → msb -p <port>:<port> → VM:<port> → nerdctl -p <port>:<containerPort>`, host==guest], merged into the publish set at `workspace.Manager.Start` via `apps.PublishedPorts`; the live `nerdctl run`/`pull` is a `hardware bring-up` item, all host-side logic unit-tested with fakes. **Apps are NOT auto-started at `ai start`** — a heavy image pull is a long in-VM exec that would block the workspace start AND every other in-VM exec for the whole pull; `Start` only publishes their ports + brings containerd up, and apps start ON DEMAND via `ai apps` (`runContainer` calls `Deps.EnsureRuntime` to bring containerd up first + retries once if the runtime is unreachable). The microVM is created with **4G** memory (`microVMMemory`) so a heavy app pull does not OOM-kill the in-VM containerd), `internal/litellm` (also the `KeyManager` virtual-key client), `internal/layout`, and `internal/tui` (the K9s-style `ai ui` management TUI — parent package + sub-packages `scope` [startup project/scope resolution + create-target validation], `views` [one bubbletea model per screen: services/projects/project/network/context/localmodels/cloudmodels/apikeys/apps/sessions/settings/create — plus `workspacelog`, which is NOT a tab but a COMPONENT embedded inside `project`], with the parent owning the alt-screen shell, tab/←→/number-key navigation (the `:` command palette was REMOVED), the create overlay, and the `tea.ExecProcess` flows; views take injected funcs over the existing package APIs and honour `ai theme`; `internal/tui/layout.go` wraps each view's body in a rounded border with a SYMMETRIC 1-line/1-col inner margin and sizes the view's table to fill the pane viewport so its bottom stays fixed while scrolling). The per-workspace sub-tabs are exactly **Workspace · Network · Context · Shell · Apps** (NO separate log tab). The **Workspace** tab (`views.Project`) shows the workspace summary on top with the **workspace log EMBEDDED beneath it** (`views.WorkspaceLog`, a component of this view, not its own tab): READ-ONLY (no command input), scrollable, selectable, auto-refreshing (`Manager.WorkspaceLogTail` → `Sandbox.LogTail` → `msb logs <vm> --tail`, re-polled ~2s, generation-guarded, shown ONLY while the workspace is RUNNING (a stopped workspace shows a "not running" hint, not the previous session's stale captured output), freezes while scrolled up else follows the tail; `f`/`enter` follows it live in the user's REAL terminal via `msb logs -f`); the polled text is passed through `normalizeTerminalOutput` (a pure pass interpreting `\r`/cursor-moves/erase-line) so progress redraws collapse IN PLACE while the full scrollback + plain selectable text are preserved. Workspace **start/stop/restart run DETACHED** (`setsid` + `Process.Release`, stdio to `/dev/null`) so the microVM build/boot survives `ai ui` being closed — the Workspace tab shows an animated spinner and polls the state handle until done (TUI stays navigable, NO log/terminal pane for these); `delete` runs in the confirm overlay. The **Shell** tab is the per-workspace **session manager** (`views.Sessions`, Title() "Shell"): it lists the tmux sessions and on the selected row attaches (`enter`/`a`), creates a new named session via an inline prompt (`n`), or kills (`d`/`k`); the interactive shell itself runs in the user's **REAL terminal via `tea.ExecProcess`** (the app suspends, runs `ai shell`/`ai attach`, restores on exit) — NOT the embedded emulator — so keys, native text selection, and in-place output all work via the host terminal. The CLI mirror is `ai shell`/`ai attach`/`ai agent`/`ai sessions` + **`ai sessions kill <session> [name]`**. **`ai ui` does NOT capture the mouse** (so the host terminal's native text selection works everywhere); scrollable panes scroll by keyboard (PgUp/PgDn/arrows). The embedded **terminal pane** (`views.Terminal`, vt10x over a `creack/pty` PTY) remains for the **non-interactive** overlays only (lifecycle start/stop/restart/delete, apps, models, keys) and keeps a plain-text **scrollback** buffer (vt10x has none) with a scroll mode (PgUp/PgDn + arrows in a non-interactive pane scroll rather than echoing as `^[[A`). The `aip-dns` CoreDNS resolver is the egress-audit backend (`ai network log`): microVMs boot with `--dns-nameserver` pointed at it, so every queried name is logged. **Version control is out of scope** — there is no git package and `ai create` runs no git. **Supported hosts are macOS (Apple Silicon) and Linux** — there is no cross-OS path-translation layer.

**State is split global vs project-local, written atomically.** Global lives under `~/.ai-platform/` (config, `runtime.yaml`, `versions.yaml`, `projects.yaml` index); per-project state lives in `<project>/.ai-platform/` (tracked `Dockerfile`/`config.yaml`/`profile.yaml`/`project.yaml`/`skills/caveman/`/`agents/` [KEYLESS agent-CLI templates], gitignored `run/`). All paths derive from `os.UserHomeDir()` via `internal/paths`, so **tests redirect with `t.Setenv("HOME", t.TempDir())`**. **All host-persisted SYSTEM data volumes live under `~/.ai-platform/volumes/<name>` (`paths.VolumesDir`, create-on-use via `MkdirAll`)** — one discoverable home so `ai uninstall --purge` (RemoveAll `~/.ai-platform`) removes them all: today `volumes/litellm-db` (the LiteLLM Postgres data dir, HOST BIND MOUNT, not a named volume) and `volumes/models` (the Ollama store) — `volumes/` is now ONLY true host data volumes. **Re-fetchable caches live separately under `~/.ai-platform/cache/<name>` (`paths.CacheDir`, create-on-use via `MkdirAll`)** — `cache/catalog.json` (the models.dev catalog, MOVED from `volumes/catalog.json` with a one-shot lazy migration in `catalog.Path`) and `cache/ollama-library.json` (the live Ollama installable-library list); both are re-downloadable copies, not SYSTEM data, and are likewise removed by `ai uninstall --purge`. Config-file mounts (LiteLLM/DNS/nginx configs under `config/`) and the per-project workspace overlays are NOT system volumes. Migration is one-shot acceptable: the old `aip-litellm-db-data` named volume / old `~/.ai-platform/models` do NOT auto-migrate (Postgres re-initdb's, models re-pull); `ai uninstall` still best-effort `docker volume rm aip-*`s the legacy named volume. All state/config writes go through `internal/conffile` (atomic YAML — temp file + `rename`; reads reject unknown fields via `KnownFields`). `versions.yaml` (`internal/versions`) is the **source of truth for the service-tier image refs** — pinned by **image + tag** (default `latest`; no digests — they are platform/arch specific) — and `internal/setup`'s `containerImage` resolves every service image from it, falling back to `versions.Default()` when the file is absent or an entry is incomplete. The `--json` output envelope (`internal/output`) and the in-workspace agent-CLI configs (`opencode.json`, `~/.pi/agent/models.json`) stay JSON. Config merges `project > global` via `internal/config` (deep map-merge).

**Dual runtime model.** Microsandbox microVMs run workspaces; Docker/Podman run the service tier on the shared `aip-net` network, reconciled in order network → DNS → Ollama → Presidio → LiteLLM(+DB) → Headroom → nginx proxy (LAST). Open WebUI is no longer a host service — it now runs as a **per-workspace in-VM app** (`internal/apps`); **Odysseus has been removed from the platform entirely** (no host containers, no docker-socket mount). There are currently NO optional host services — the optional MECHANISM is retained (empty set) for future use. **`aip-proxy` (nginx) is the SOLE host entry point to the service tier: every other service container is INTERNAL-ONLY on `aip-net` (reached by name) — only nginx publishes ports to the host** (besides the loopback-only `aip-litellm-db` :5442 and `aip-dns` :15353). The services: `aip-dns` (CoreDNS egress-audit resolver, bound to host loopback `127.0.0.1:15353/udp`; microVMs use it via `--dns-nameserver`), `aip-ollama` (required local models, INTERNAL-ONLY — no host publish — reached by name at `http://aip-ollama:11434` and from the host via nginx's `/ollama` route; models persist on the host at `~/.ai-platform/volumes/models`), the `aip-presidio-analyzer`/`aip-presidio-anonymizer` pair backing LiteLLM's always-on secret-masking guardrail, `aip-litellm` (the gateway, INTERNAL-ONLY — no host publish — reached by name at `aip-litellm:4000` by Headroom and by nginx's `/llm` route) plus a small `aip-litellm-db` Postgres (trust auth, host port 5442 loopback; its data dir is a HOST BIND MOUNT from `~/.ai-platform/volumes/litellm-db` at `/var/lib/postgresql`, NOT a Docker named volume) that backs LiteLLM's DB-backed admin UI/virtual keys + the encrypted provider-credential store (the one stateful service-tier piece), `aip-headroom` (the input-compression proxy in front of LiteLLM, `OPENAI_TARGET_API_URL=http://aip-litellm:4000`, `HEADROOM_NO_CCR_INJECT_TOOL=1`; pulled image, never built — INTERNAL-ONLY on :8787 behind nginx, no host publish), and `aip-proxy` (the `nginx:stable-alpine3.23-slim` reverse proxy, the SOLE host ENTRY: on host :18787 it fronts the model path `location /v1` → `aip-headroom:8787` [the agent chat path, PRESERVED unchanged], the LiteLLM admin surface `location /llm` → `aip-litellm:4000` [prefix stripped: `/model/info`, `/v1/models`, `/health*`, `/key*`, `/credentials`], and the Ollama API `location /ollama` → `aip-ollama:11434` [prefix stripped] — specific prefixes before the catch-all `/` [the DEFAULT route, also → Headroom]; the model path `/`+`/v1` ride Headroom, while `/llm`/`/ollama` and the UI vhost BYPASS it; the SOLE web UI vhost is now **`litellm.<domain>` → `aip-litellm:4000`** [admin UI at `/ui`; always, litellm is core] on the SAME :18787 — NOT a separate host port; SSE-friendly — buffering off, long timeouts; the per-vhost HTTPS termination point later, binds 0.0.0.0:18787 in server mode; reconciled LAST so its upstreams are up first — nginx resolves a literal `proxy_pass` host at config-load. The `<domain>` is the resolved platform base domain (`runtime.yaml` `domain`, default `aip.local`, threaded through `ensureProxy` via `reconcileDomain()`); **standalone** `ai setup` writes an `/etc/hosts` managed block (consent + sudo via `uihosts.SyncHosts`, else a printed manual block) pointing the UI subdomain (`litellm.<domain>`) at `127.0.0.1`, **server** prints the DNS (`*.<domain>` → server) + TLS-at-nginx operator contract (`uihosts.ServerGuidance`, no `/etc/hosts` edit), both surfaced in `ai doctor` too; the UI→subdomain map is declared ONCE in `internal/services` (`Service.UISubdomain`/`UIVhosts`) and consumed by `internal/uihosts` (+ setup/doctor/uninstall, which removes the standalone hosts block on teardown). The live UI-vhost routing and the sudo `/etc/hosts` write (`hostsfile.Plan` → temp file → `sudo cp`) are `hardware bring-up`. The host CLI reaches LiteLLM (admin via `localhost:18787/llm`, the chat test via `localhost:18787/v1` to exercise the real Headroom→LiteLLM model path) and Ollama (via `localhost:18787/ollama`) through nginx, never a container directly (`litellm.AdminBaseURL`/`GatewayBaseURL`, `ollama.DefaultBaseURL`); the agent microVM `/v1` path (`host.microsandbox.internal:18787/v1` → Headroom) is preserved unchanged. Live end-to-end routing through these nginx routes is a `hardware bring-up` item. There is no native firewall service; provider credentials live in LiteLLM (keys-in-LiteLLM). Detection (`internal/runtime` + `internal/sandbox`) is parameterized by `GOOS/GOARCH` + a `Prober` so it tests on any host; missing deps → exit 3, missing rootless/virtualization → exit 4. macOS requires **Apple Silicon** (no Intel). **Deployment roles** (chosen interactively by `ai setup`, or `--mode`, persisted as `role:` in `runtime.yaml`): **standalone** (default — full service tier + workspaces here; shared services bind **127.0.0.1**), **server** (only the service tier, bound **0.0.0.0** for remote clients, no workspaces — preflight needs only docker + rootless), **client** (only workspaces; routes to a remote `--server` address held in `ai_platform_host`, skips the local reconcile — preflight needs only msb + virtualization). The role drives `blockingPrereqsForRole` and the `bindHost` threaded through `Services.Reconcile`/`ensure*` (Postgres + DNS stay loopback regardless); since the service containers are now internal-only, `bindHost` governs only what **nginx (`ensureProxy`)** publishes (the sole host entry — `litellmRunArgs`/`ensureOllama` no longer publish), and `RelaunchLiteLLMWithAuth` still derives its bind from the persisted role via `currentBindHost()` for the proxy. Per-project workspace egress is declared via `ai network` (modes public[default,allow-outbound]/deny/unrestricted, allowed host services incl. domains + `*.suffix`, published ports, stored in `config.yaml`) and applied as Microsandbox net-rules (`egress.MsbNetworkArgs`; the default-deny fallthrough still blocks private ranges under `public`, and the always-on host-gateway + DNS allow rules stay) at workspace create. Host-reaching rules MUST target msb's `host` GROUP token (`allow:egress@host:tcp:<port>`), NOT the `host.microsandbox.internal` NAME: only the `host` group engages msb's host-forwarding — a host-NAME target lets the guest connect to the msb gateway but is never forwarded to the host service (empty reply, verified live). So the LOCAL gateway rule + the `gateway`/empty host-service allow-list entries + the always-on DNS pair (`Rule::allow_dns()` = `host:udp:53` + `host:tcp:53`, required so DNS resolves under default-deny) all use the `host` group; a remote gateway (client mode) and explicit domain/IP host-services stay verbatim. **Model gateway wiring** (`ai gateway show|set|clear`, `internal/cli/gateway.go`): the machine-wide `ai_platform_host` in `runtime.yaml` (set by `ai gateway set <host[:port]>` or `ai setup --mode client --server`) selects which gateway every workspace microVM on this host routes through. `internal/workspace` derives it at start via `runtime.ResolveGateway(Info.HostAddress())` — bare host or `host:port`, default port 18787; empty → `host.microsandbox.internal:18787` (standalone/local) — and uses the resolved `http://<host>:<port>/v1` for the agent provider configs' `base_url` and the resolved `<host>:<port>` for `MsbNetworkArgs(network, gatewayHost, gatewayPort)`'s always-on egress allow rule. `ai gateway` exits 3 (no runtime.yaml — run `ai setup`), 2 (invalid address), 4 (persist/read failure). **Platform base domain** (`ai domain [name]`, `internal/cli/domain.go`): the machine-wide `domain` field in `runtime.yaml` is the base domain the nginx UI subdomains hang off — `litellm.<domain>` (the SOLE host UI vhost now) — defaulting to `aip.local` (`runtime.DefaultDomain`, resolved via `Info.ResolveDomain()`/`runtime.ResolveDomain`) for local/standalone and overridden in server mode. `ai domain` with no arg SHOWS the resolved domain; with a name it VALIDATES a lowercase DNS hostname (labels of `[a-z0-9-]`, no scheme/path/whitespace, no leading/trailing dot) and persists it, mirroring `ai gateway`'s load-modify-save + exit codes (3 no runtime.yaml, 2 invalid, 4 persist/read). This `domain` is wired into the nginx UI vhost + the standalone `/etc/hosts` block (see the Dual runtime model above).

**Model catalogue is global, DB-backed, and catalog-driven.** Models are registered in LiteLLM's Postgres-backed model store (`general_settings.store_model_in_db: true`) — the rendered `config.yaml` has NO `model_list`, NO named aliases, NO per-provider wildcards, and NO default model (`litellm.DefaultRouting()` now returns the ZERO `Routing` — empty `Default`, empty `Aliases`). The model set is driven by the **models.dev catalog** (`internal/catalog`, fetched to `~/.ai-platform/cache/catalog.json` at `ai setup` and on the Cloud Models tab `r` key — one-shot migrated from the legacy `volumes/catalog.json`; `catalog.LoadOrFetchStatus` reports the data `Source` fresh-vs-cached so the UI can message availability): adding a provider API key via `ai keys` syncs that provider's catalog models INTO the DB, removing it syncs them OUT (`litellm.SyncModels`; the catalog-id→LiteLLM-prefix map is e.g. `google`→`gemini`, and the public `model_name` registered is the catalog id verbatim), while Ollama models are registered/unregistered as DB-backed models by `ai models pull`/`rm` (`litellm.RegisterOllamaModel`/`UnregisterOllamaModel`, public `model_name` `ollama/<name>`). The in-workspace agent names any served model per request and LiteLLM routes it (real provider keys live in LiteLLM; the agent authenticates to the gateway with a scoped virtual key, Ollama needs none) — there is **no per-project model config**. LiteLLM's generated config renders **always-on guardrails** (all `default_on: true`), scoped to **secrets/credentials, not general PII**: `presidio-secrets-input` (pre_call) + `presidio-secrets-output` (post_call) mask only financial/identity secrets (CREDIT_CARD, US_SSN, US_BANK_NUMBER, IBAN_CODE, CRYPTO — see `secretEntities`), plus `hide-secrets` (LiteLLM's in-process detect-secrets) for API keys/tokens. Masking general PII (names, places, emails) was deliberately removed — it corrupted ordinary coding prompts. Additionally, a **tool firewall** (`guardrail: tool_permission`, `mode: post_call`) DENIES destructive command tool-calls (`git push --force`, `rm -rf`, `terraform destroy`, `kubectl delete`, … — `destructiveCommandPatterns` in `internal/litellm`) — for coding agents the bigger risk is destructive tool execution, not prompt content. The in-process **prompt-injection** callback (`detect_prompt_injection`) was REMOVED — like the unmaintained **LLM Guard** (also removed) it false-positived on ordinary coding/Ollama traffic; Guardrails AI (needs a Hub token + per-guard install) remains **deliberately deferred**. Because default-on guardrails run on every request and all routes (cloud included) traverse the proxy, cloud calls cannot bypass them. Registering a model ≠ installing it (an Ollama model still needs pulling — via `ai models pull`; a cloud model still needs its key). **Ollama model management** is `ai models` (`internal/cli/models.go`+`models_local.go`, over the injected `ollama.Client`/`litellm.Client`): `status` (LiteLLM health + the served/provider view sourced LIVE from the gateway — `/model/info` → `/v1/models`, not from any aliases — plus Ollama connectivity), `test [model]` (round-trips a model through the gateway), `list` (installed local models), `popular` (the live installable library), `pull [name...]` (downloads into the local Ollama store — names/`--json` pull each ref in turn; a TTY with no args checks off library `name:tag` refs + an optional custom-ref entry; re-pulling updates, there is no separate update verb), `rm [name]` (removes a local model), and `show <name>` (model metadata). The installable library is fetched LIVE from the ollama.com library endpoint (`internal/ollama/library.go` — `ollama.Library()` GETs `https://ollama-models.zwz.workers.dev/`, a JSON `[{name, description, tags}]`; each model's `RepoURL` is DERIVED as `https://ollama.com/library/<name>` since the endpoint carries none), cached at `~/.ai-platform/cache/ollama-library.json` and falling back to that cache when the endpoint is unreachable (`LoadOrFetchLibrary` reports `Source` fresh-vs-cached). There is NO bundled `models.yaml` and no offline fallback set — the library has no per-tag download size, so `ai models popular` shows SIZE as "—" and its refs are `name:tag`. The `ai ui` TUI splits models into a **Local Models** tab (`internal/tui/views/localmodels.go`) and a **Cloud Models** tab (`internal/tui/views/cloudmodels.go`) — there is no single combined "Models" tab; the top-level view order is Services · Workspaces · Local Models · Cloud Models · API Keys · Settings. Local Models lists an **Installed** section (library models with ≥1 pulled tag, plus installed customs) + an **Installable** section (the rest of the live library), rendered as a custom **viewport-windowed list** (NOT a bubbles table, so the section headers can be styled) showing **NAME · DESCRIPTION only — there is no TAGS column** (tags live solely in the per-model drill-down), with a per-model **tag drill-down** (`enter`) to space-select 1+ NOT-installed tags then `enter`/`p` to pull (emitting `ModelsPullRequestedMsg{Refs}` → `ai models pull <refs…>`), `d` to remove an installed tag, `t` to test one (and `enter` on an installed tag opens its `/api/show` detail) — list keys `enter` manage tags · `t` test · `d` remove · `r` refresh; Cloud Models lists the models.dev catalog ⨯ the gateway's live registered set in a bubbles MODEL · PROVIDER · STATUS · CONTEXT table, showing ONLY models for keyed/registered providers (it EXCLUDES local `ollama/<name>` models) — `enter` details · `t` test (registered) · `r` refresh catalog + resync (provider keys stay in the API Keys tab — PROVIDER · NAME · KEY? · MODELS; `a` add · `e` edit (overwrite) · `d` delete · `r` refresh, `esc` backs out of the add/edit overlay, and the key VALUE never enters the view). When models.dev OR the ollama library endpoint is unreachable, each view uses its cached copy and flashes a source-availability message; with no cache it shows the message + an empty section. `ai services start|stop|restart` manage the whole platform container set (ollama, presidio, litellm, headroom, proxy, dns); `ai services update [service]` (and the TUI Services pane's `p` key) force-RE-PULLS the latest images (`Services.UpdateImages` — unlike the first-run `PullImages` it does NOT skip already-present images, so a moved `latest` tag is refreshed) then restarts the target so its container is recreated against the new image (`setup.UpdateService`); ClawPatrol is gone and there is no native service to manage. The LiteLLM admin UI is secured with `UI_USERNAME`/`UI_PASSWORD`/`LITELLM_MASTER_KEY` passed by **env passthrough** (values never in argv/config/disk). **Role-based UI-auth policy** (`runtime.RequireUIAuth(role)`, true ONLY for `server`): standalone/client run OPEN — `ai setup` does NOT prompt for a LiteLLM password; a server REQUIRES a password (`ai setup` loops on a TTY until non-empty, generates one non-interactively rather than leave the gateway open). (The in-VM Open WebUI app sets its own `WEBUI_AUTH`; the removed host Open WebUI/Odysseus services no longer factor in here.) A standalone user opts into a password later via **`ai litellm password`** (`internal/cli/litellm.go` — prompts hidden, reuses the running master key else mints one, `RelaunchLiteLLMWithAuth`; exit 3 if not set up / client / gateway down, 2 on bad/empty/non-TTY input, 4 on relaunch failure). Both `ai setup` and `ai litellm password` then OFFER to persist `UI_PASSWORD`+`LITELLM_MASTER_KEY` to **`~/.ai-platform/.ai-platform.env`** (`internal/envfile` — opt-in **0600** `export KEY='VALUE'` file, auto-loaded at `ai` startup in `root.go` `PersistentPreRun` before `ui.Apply`; existing env WINS, file only fills gaps) so they survive restarts with no shell-rc edit; on decline / non-TTY the manual `export …` block is printed.

**The CLI surface is FLAT: workspace management lives in top-level verbs** (CLI §3/§4) — `ai create`/`ai list`/`ai delete` (create/list/delete a workspace; **`ai delete` is the single removal verb — `destroy` is now an ALIAS of it**, not a separate VM-only teardown: a plain delete tears down the microVM, removes the project's `.ai-platform` dir + overlay, and de-registers it from `projects.yaml`, keeping the user's OTHER files; `--purge` removes the whole project directory) and `ai start`/`ai stop`/`ai restart`/`ai exec`/`ai shell`/`ai agent`/`ai attach`/`ai sessions`/`ai apps` (microVM lifecycle + sessions + in-VM apps), each taking an OPTIONAL `[name]` resolved via `resolveProjectName` (explicit name → `--project` → cwd workspace). The grouped `ai workspace …` / `ai project …` commands were **removed** — the flat verbs are the only surface (their shared RunE bodies live in `internal/cli/workspace.go` as `workspace*RunE`, plus the `newCreateCmd`/`newListCmd`/`newDeleteCmd` constructors in `project.go`; the envelope `command` keys stay `workspace.*`/`project.*`). The user-facing noun is **"workspace"** in all help/messages/TUI labels, but internal package/type/field names (`internal/project`, `project.Entry`, `state.Project`, `views.Projects`/`ProjectsHub`) and JSON data keys (`{"project": …}`) keep "project" for stability. NB: `ai doctor [name]` is **consolidated** — it always reports platform health + every service-tier service (ollama, presidio, litellm, headroom, proxy, dns), and ADDITIONALLY the workspace-runtime checks (rootless + virtualization) when inside a workspace dir (cwd/ancestor) or given `[name]`; there is no separate `ai workspace doctor`. It always exits 0 with a report (per-check status conveys health).

**`ai create` is an in-process `charmbracelet/huh` wizard** (CLI §3.1): workspace name, OS (`debian-trixie`/`debian-bookworm`/`ubuntu`/`alma`), agent CLIs (multi-select: `opencode`/`pi`/`claude-code`/`codex`/`gemini` — `opencode` (default tool) and `pi` are installed by default, both wired to LiteLLM), default agent CLI, and software stacks (`go`/`node`/`python`/`rust`/`java`/`maven`/`deno`) are picked across the wizard's five groups. Every input also has a flag (`--name`/`--os`/`--agents`/`--stacks`); on a TTY the flags **pre-seed** the wizard (which always shows — flags are never required there), while under `--json` or no TTY the spec is built straight from the flags with no prompt and `--os` is **required** (a missing `--os` exits 2). The workspace is created **in the current directory** (no fixed `~/projects`); if the cwd is already a workspace it **attaches** instead. The platform runs **no git** (VCS is out of scope). `--dry-run` emits the side-effect-free action plan. The command itself uses no PTY; automation drives it through a pseudo-terminal (`creack/pty`) only via the acceptance harness in `test/acceptance` (§1.4).

## Conventions

- **Commands prompt on a TTY** (CLI §1.8), via the shared helpers in `internal/cli/prompt.go` (`interactive`/`runForm`/`promptText`/`promptSecret`/`promptChoice`/`promptMultiChoice`, all built on `charmbracelet/huh`). On a terminal the prompt ALWAYS shows, **pre-seeded** with any value given as an arg/flag (the user confirms/edits — the value never silently bypasses the TUI); only under `--json`/no-TTY is a provided value used directly, with a missing required value erroring (exit 2) so automation stays scriptable. Two exceptions: a **hidden credential value** (`ai keys add --value/--stdin`) is used directly even on a TTY (a hidden field can't show a seed), and `ai services start|stop|restart` act directly on an explicit name/`all` and only show the checkbox with no arg. Known option sets are shown as selects/checkboxes. **All of a command's prompts must share ONE `runForm`** so the user can navigate back between them — never chain separate prompt calls. The TUI look-and-feel is **theme-selectable**: `internal/ui` owns a registry of named themes (huh built-ins `default`/`dracula`/`catppuccin`/`base16`/`monochrome` plus custom palettes in `custom_themes.go` — `orange`/`synthwave`/`cyberpunk`/`tokyo-night`/`nord`/`gruvbox`/`onedark`/…, each wrapping a huh theme + heading accent; `ui.TableStyles()` themes the `ai ui` tables with the active accent), persisted per host in `~/.ai-platform/config/ui.yaml` and applied once at startup (root `PersistentPreRun` → `ui.Apply(ui.LoadThemeName())`); `ai theme [name]` shows/selects it (the semantic status colours stay fixed across themes).
- **No single-character variable names anywhere** — including method receivers and loop vars (`store`, `emitter`, `prober`, `entry`, `value`, …). Self-documenting names over Go's terse-receiver convention. The one kept exception is the test handle `t *testing.T`.
- **Provider API keys never touch platform disk.** Keys flow straight to the LiteLLM credential store (encrypted at rest by `LITELLM_SALT_KEY`) via `litellm.KeyManager` (`SetCredential`/`DeleteCredential`/`ListCredentials`), which `ai keys` fronts; `ListCredentials` returns names + provider prefixes only (never values), so listings can't leak. `ai keys` is catalog-driven (`internal/catalog`, models.dev): a key is keyed per LiteLLM-routable provider, and `add`/`remove` sync that provider's catalog models into/out of the gateway (`litellm.SyncModels`). It **replaced** the former `ai secrets` command and the `internal/secrets` package.
- **Parallelize with subagents + git worktrees where the work is disjoint — but never at the cost of merge chaos.** When a task decomposes into independent units that touch *different* files, prefer launching multiple subagents in parallel, each in its own git worktree (`isolation: worktree`), then integrate by pulling each branch's files (`git checkout <branch> -- <files>`). Do NOT parallelize units that edit the **same** file (notably `internal/setup/setup_real.go`, `internal/tui/tui.go`) — sequence those instead. The rule that keeps integration clean: each agent owns a **disjoint file set**, and the parent does any shared wiring (e.g. registering new views in `tui.go`) itself. If you can't partition the work into disjoint file sets, do it single-threaded.
- Commit messages must not include AI-attribution trailers (no `Co-Authored-By` for the assistant). Commit only when asked; the work lives on a feature branch off `main`.
