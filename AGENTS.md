# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, and any tool that reads `AGENTS.md`) when working with code in this repository.

## What this is

The `ai` CLI — the single control-plane binary for the **AI Development Platform**: reproducible, isolated AI dev environments where workspaces are hardware-isolated **Microsandbox microVMs**. The model path runs agent → host **nginx** gateway → **LiteLLM** routing (with a **user-selectable guardrail set** chosen at `ai setup` — the **Headroom** input-compression `pre_call` guardrail is the only one ON by default; **Presidio** secret-masking, detect-secrets, and the destructive-command tool-firewall are opt-in — each enabled one applied in-process on every request; the Presidio containers start only when secret-masking is selected) → containerized **Ollama** or a cloud provider; Headroom, Ollama, Presidio, and LiteLLM are all shared host containers (Headroom is NO LONGER an nginx proxy in front of LiteLLM — nginx forwards the model path DIRECTLY to LiteLLM, and LiteLLM's `headroom` guardrail POSTs the request messages to `http://aip-headroom:8787/v1/compress` to compress them before dispatch [requires LiteLLM v1.92.x+; the litellm image is TEMPORARILY pinned to `v1.92.0-rc.1`, revert to `latest` once the guardrail ships stable]; separately, Headroom is now ALSO installed inside each workspace image — `uv tool install "headroom-ai[proxy]"` (the `proxy` extra only — NOT `[all]`, which drags in torch/CUDA/opencv/rapidocr via the `ml`/`image`/`voice` extras and blows up the image build) — so each agent CLI can be wrapped in-VM via `headroom wrap <cli>`, wired in a follow-up that will move compression into the sandbox). Each workspace image also ships `zsh` + oh-my-bash + oh-my-zsh (the per-workspace default-shell choice, bash or zsh, is a first-class create input — `--shell`/the wizard, `config.Workspace.Shell`, default `bash` — applied at every workspace start by `workspace.Manager.applyShellChoice`, which idempotently appends the managed agent-env/alias block to both `~/.bashrc` and `~/.zshrc` and, when zsh is chosen, `chsh`es the workspace user's login shell to zsh). **Caveman** is the per-project in-workspace output-compression toolkit — NO LONGER a platform-written one-file stub: it is installed by Caveman's OWN installer (`https://raw.githubusercontent.com/JuliusBrussee/caveman/main/install.sh`) at workspace START (`workspace.registerCaveman`, once-guarded, network-bound, best-effort), which gives each caveman-detectable CLI (claude-code/opencode/gemini/codex — mapped to `--only <agent>`; pi/omp/copilot are NOT detectable) its native skills+agents+commands PLUS the CLI-native extras the shared pool cannot carry (opencode plugin, claude hooks + statusline, gemini extension). Because pi/omp read skills ONLY from the shared `.ai-platform/skills` pool, `registerCaveman` then MIRRORS opencode's GLOBAL caveman dirs (`~/.config/opencode/{skills,agents,commands}`) into the pool (skills→skills, agents→agents, commands→prompts) so the existing symlinks distribute them to pi/omp. `ai context caveman <project> <level>` sets `Context.CavemanLevel` in config (advisory — the installed skill controls intensity at runtime via `/caveman <level>`). Credentials are **keys-in-LiteLLM**: real provider API keys are added via `ai keys` and live ENCRYPTED in the LiteLLM gateway's Postgres credential store (encrypted at rest by `LITELLM_SALT_KEY`), never on platform disk, in `config.yaml`, or in the workspace — the agent holds only a scoped LiteLLM **virtual key**. The served model set is catalog-driven (models.dev) and DB-backed: adding/removing a provider key syncs that provider's models in/out of LiteLLM's DB, so there is no `model_list`/wildcards/named aliases in the rendered config. Workspace egress is a per-project Microsandbox NetworkPolicy configured via `ai network` and applied as `msb` net-rules at workspace create; the **default mode is now `public`** (allow-outbound — private ranges still blocked; lets the in-VM container runtime pull images and AI processes reach the internet), with `deny`/`unrestricted` as the re-lockable alternatives; attempted egress is audited by domain name via the `aip-dns` resolver (`ai network log`). Every workspace microVM also ships a **rootful in-VM OCI container runtime** (containerd + nerdctl + runc + CNI, from the pinned `nerdctl-full` tarball in every OS base Dockerfile), started best-effort at workspace start. Secret/credential masking is available as opt-in LiteLLM guardrails — Presidio scoped to financial/identity secrets plus the in-process `hide-secrets` detector — which, WHEN ENABLED at `ai setup`, cloud routes cannot bypass. For coding agents the bigger risk is destructive **tool execution**, so an opt-in LiteLLM `tool_permission` **tool firewall** denies dangerous command tool-calls (`git push --force`, `rm -rf`, `terraform destroy`, `kubectl delete`, …) at the gateway. These guardrails are chosen from a picker at `ai setup` and persisted in `runtime.yaml`; only the **Headroom** input-compression guardrail is on by default, and the **Presidio containers are launched only when secret-masking is selected**. (The in-process `detect_prompt_injection` callback AND the unmaintained LLM Guard were both removed — crude heuristics that false-positived on ordinary coding/Ollama traffic, rejecting it with "Rejected message. This is a prompt injection attack.") Go 1.26, a single self-contained binary — **cgo** now, since it links the Microsandbox **Go SDK** (a cgo binding that dlopens an embedded FFI library; the bytes are `go:embed`-ed and extracted at first run, so it is still one binary, but `CGO_ENABLED=1` is required and the old pure-static build is gone). Module `github.com/jt-helsinki/stack-genie`.

**`spec/` is the source of truth, not documentation.** The six numbered specs define the end-state architecture (`01`), delivery slices (`02`), on-disk/repo layout (`03`), the exact CLI surface + JSON envelope + exit codes (`04`), acceptance tests (`05`), and the milestone build plan (`06`). Code comments cite spec sections (e.g. `§17`, `CLI §3.1`, `repo-layout §12.5`) — when changing behavior, read the cited section first and keep code and spec in sync. The build proceeds in milestones **M0–M8** (see `spec/06`), with later work organized as slices **S1–S6** (`spec/02`). The full surface is implemented (M0–M8 plus slices S1, S2, S4–S6; S3 and S7 retired) — host-side **and**, on a provisioned Apple Silicon host, the live external-tool integration: `ai setup` launches the service-tier containers (DNS audit resolver, Ollama, Presidio, LiteLLM + its DB, Headroom); LiteLLM mints scoped agent virtual keys and holds provider keys; workspace microVMs build, boot, and exec; the per-project `ai network` egress policy is applied as Microsandbox net-rules at workspace create; and the DNS egress audit (`ai network log`) works — all verified end-to-end this cycle. The narrow seams that still depend on further bring-up (live microVM (`msb`) log follow, live `nerdctl run`/`pull` in the workspace, and live end-to-end confirmation of the tool-firewall + nginx routes against the running stack) are grep-able (`hardware bring-up`) and tracked in `docs/HARDWARE-BRINGUP.md`. Before changing a slice, read its milestone in `spec/06` and its `[Sx]`-tagged tests in `spec/05`.

CI (`.github/workflows/ci.yml`) is split: hosted runners do build/vet/lint/unit-tests; a self-hosted **Apple Silicon** runner runs `[S1]` acceptance (the only host that can run the full stack). ## Architecture (the parts that span files)

**Output envelope is the universal contract.** Every command returns the `internal/output` envelope (`{ok, command, data, error, warnings}`, CLI §19). `error.code` **equals** the process exit code (§18: 0 ok, 2 invalid input, 3 missing dependency, 4 runtime failure, 5 permission). Pattern: `Execute()` (in `internal/cli/root.go`) owns an `exitCode` int and an `Emitter`; each cobra command's `RunE` does its work and sets `*exit = emitter.Success(...)` or `emitter.Failure(...)`, returning `nil`. Errors that must carry a specific exit code are `*output.Error` (build with `output.Errorf(code, ...)`); the emitter unwraps them. cobra/arg errors are mapped to exit 2 in `Execute`. Output is **human-readable by default**; the JSON envelope is emitted only with `--json` (commands provide a typed result + a Human renderer — see `ai logs`).

**Workspace backend: the in-process Microsandbox Go SDK is the DEFAULT.** `internal/workspace` has two implementations of the `Sandbox` interface: `sdkSandbox` (`workspace_sdk.go`, the default — drives microVMs via the `github.com/superradcompany/microsandbox/sdk/go` cgo SDK, holding ONE reused relay connection per workspace; create/exec/FS/logs/metrics/SSH-attach all go through it) and `realSandbox` (`workspace_real.go`, the legacy `msb`-CLI shell-out, selected with `AIP_WORKSPACE_BACKEND=cli` as an escape hatch). `selectSandbox` picks between them. The SDK backend fixed the relay-client-exhaustion wedge by collapsing per-call `msb exec` connection churn into one handle (see docs/MSB-SDK-MIGRATION.md); logs stream over the SDK's relay-free `LogStream`, and metrics stream over `sb.MetricsStream`. Live-validated on Apple Silicon (msb 0.6.1); the interactive Attach + full create→start flow are TTY/host bring-up items. **`ai create` resolves CPU/memory (host-capped via `internal/sysinfo`) + published ports + location, and the microVM is SDK-created.** **Keep-alive:** msb boots the microVM running the image's entrypoint/cmd and STOPS the sandbox when it exits — a plain image's default shell exits on the detached VM's empty stdin — so the workspace is pinned open two ways: the SDK create passes `WithEntrypoint("sh","-c","exec sleep infinity")` (keeps the VM up regardless of the image cmd, so even an image predating the change survives a recreate) AND every OS base Dockerfile sets `CMD ["sleep","infinity"]` (covers the CLI backend + is self-contained); all real work runs via `Exec` (tmux sessions / agent CLIs), the anchor process is just the keep-alive. When reading the older "msb shell-out" descriptions below, treat the SDK backend as the live path and the `msb …` invocations as the CLI-backend equivalent.

**External tools sit behind injectable interfaces; logic is faked in tests.** Docker/Podman, the Microsandbox runtime (`msb`/SDK), Ollama, and LiteLLM are never called directly from orchestration code. Instead: `runtime.Prober`, `setup.Services`, `litellm.KeyManager`, `litellm.Client`, `ollama.Client`. Orchestrators (`internal/setup`, etc.) take these via a `Deps`-style struct and are unit-tested with fakes; real implementations live in `*_real.go` and are wired by the CLI. Most of these real impls are now wired and verified on Apple Silicon — the service-tier container launches, LiteLLM key minting + provider-credential storage (`litellm.KeyManager` → LiteLLM `/credentials`, encrypted at rest, fronted by `ai keys`), the workspace OCI build + `msb` microVM lifecycle (`workspace.Builder`/`Sandbox` — `Exec` one-shot/buffered as `workspace`, `ExecRoot` one-shot as image ROOT via `msb exec -u root` [msb's no-`-u` default is the unprivileged `workspace` user (uid 1000), NOT root; used to boot the rootful in-VM containerd], `ExecInteractive` a real PTY via `msb exec -t -u workspace` backing `ai shell` + the TUI **Shell** tab's `enter`/`a` attach via `tea.ExecProcess`), and the `ai network` egress policy applied as `msb` net-rules. Every workspace VM now ships a rootful in-VM OCI runtime (containerd + nerdctl + runc + CNI from the pinned `nerdctl-full` tarball in each OS Dockerfile); `Manager.Start` brings containerd up best-effort via `ensureContainerd` (probe `nerdctl info` quietly — `sh -c 'timeout 5 nerdctl info >/dev/null 2>&1'`; else boot `setsid containerd &` then POLL `nerdctl info` for TRUE readiness (the daemon serving requests, NOT merely the socket file existing) so the daemon both establishes and serves before the exec returns — msb tears down the exec's process group on return, which would otherwise kill the just-forked daemon; verified live on Apple Silicon). **Workspace sessions are tmux-transparent:** every shell + agent CLI runs in a persistent, reattachable per-name **tmux session** inside the microVM (one atomic `tmux new-session -A` — create-or-attach — via `ExecInteractive` as the `workspace` user; the tmux server daemonizes so the session PERSISTS after a DETACH and is listed by `ai sessions`, ending only when its shell exits. A single interactive command avoids the race where a separate detached create then attach let msb tear down the create exec's process group before the attach connected, bouncing the user back to the TUI), with a managed `~/.tmux.conf` (`agentcfg.TmuxConfig`, mouse-scroll on / status bar off) written at workspace start so the user never types a tmux command — surfaced by `ai agent <cli> [name]` (per-CLI session), `ai shell [name]` (on a TTY: a picker to ATTACH an existing session or CREATE a new named one — default new name `shell`; `--session <s>` skips the picker), `ai attach [session] [name]` (attaches an EXISTING session — explicit `[session]` attaches directly, else it lists them to pick; with NO sessions it prints a hint pointing at `ai shell`, never creates), `ai sessions [name]` + `ai sessions kill <session> [name]` (and the TUI **Shell** sub-tab); `Manager.Shell/Agent/Attach/ListSessions/KillSession`. The VM is **headless**: the agent's PTY byte stream is rendered by the user's **host** terminal emulator (WezTerm/Ghostty/iTerm — a modern one is recommended for OpenCode), so correct rendering of modern TUI CLIs is a terminfo + tmux-config problem, not a VM-side emulator. Each base image ships `ncurses-term` (the `tmux-256color` terminfo entry) and `TmuxConfig` sets `default-terminal "tmux-256color"` + `terminal-features ",*:RGB"` (24-bit truecolor) + `",*:extkeys"`/`extended-keys on`/`extended-keys-format csi-u` (CSI-u extended keys emitted in the csi-u form, so OpenCode's shift+enter / ctrl-combos survive tmux), requiring tmux ≥ 3.2 (all four bases qualify). Known limitation: tmux does **not** pass GPU/graphics protocols (kitty graphics, sixel) through, so a TUI's image rendering won't work inside the session. **The few genuinely-unwired seams are commented `hardware bring-up`** (live microVM (`msb`) log follow, live `nerdctl run`/`pull` in the workspace, and live end-to-end confirmation of the tool-firewall + nginx routes against the running stack). **Do not invent the external tools' CLI/API invocations** — verify against the real tool's docs (msb/CoreDNS/Presidio commands and the LiteLLM/Ollama HTTP APIs were verified empirically) or leave the seam and mark it deferred.

**Newer packages worth knowing.** `internal/ollama` (required local-model service, run as the `aip-ollama` container), `internal/contextopt` (Headroom strategy + Caveman level, per-project, surfaced by `ai context`; the strategy maps to Headroom's per-request `keep_turns`/`output_buffer_tokens` body knobs baked into the agent's `extra_body` at workspace start — `HeadroomParams`; these agent-side `extra_body` knobs are UNCHANGED by the guardrail rewiring, though whether LiteLLM's `headroom` guardrail forwards them to `/v1/compress` is a hardware-bring-up check), `internal/overlay` (S4 per-workspace persistence), `internal/envimage` (workspace OCI image build from the project Dockerfile), `internal/console` (admin-dashboard URL registry for `ai services console`), `internal/templates` (embedded OS/stack/agent-CLI snippets), `internal/uninstall` (native `ai uninstall` teardown), `internal/egress` (per-project workspace egress policy — mode + allow-list + published ports, surfaced by `ai network`; `MsbNetworkArgs` renders it into `msb` net-rules), `internal/agentcfg` (the in-VM agent provider config (re)loaded into the microVM on EVERY workspace start/restart by `workspace.registerAgentProviders` — base_url → host nginx gateway `:18787` (which forwards to LiteLLM directly), the scoped virtual key, and the project's `HeadroomParams` as opencode request body knobs. **The six gateway-capable agent CLIs route through the gateway by default** (copilot is the exception — see below), each config written at that CLI's OWN DEFAULT PER-PROJECT LOCATION inside the bind-mounted project dir (`<project>/…` on host = `/home/workspace/project/…` in-VM — the project is self-describing) and KEYLESS: opencode → `<project>/.opencode/opencode.json` (`apiKey:"{env:AIP_GATEWAY_KEY}"`; the env file exports `OPENCODE_CONFIG` pointing opencode at it); pi → the GLOBAL in-VM `~/.pi/agent/models.json` (the path pi ACTUALLY reads — a project `.pi/models.json` is NOT read; written into the VM via `Sandbox.WriteFile`, keyless `apiKey:"$AIP_GATEWAY_KEY"`, off host disk, so pi lists the SAME served models as opencode) + `<project>/.pi/settings.json` (defaultProvider + defaultModel + skills/prompts resource paths); claude-code → `<project>/.claude/settings.json` (an `env` block with `ANTHROPIC_BASE_URL` at the gateway ROOT — no /v1, it appends /v1/messages; the token stays in the exported `ANTHROPIC_AUTH_TOKEN`, no key in the file); codex → `<project>/.codex/config.toml` (KEYLESS `[model_providers.aip-gateway]` — `base_url=<gateway>/v1`, `wire_api="responses"` (codex requires the Responses API, which LiteLLM exposes), `env_key="AIP_GATEWAY_KEY"`) PLUS a global in-VM `~/.codex/config.toml` trust entry (`[projects."/home/workspace/project"] trust_level="trusted"`, off host disk) so codex loads the project config; gemini → ENV-ONLY (no settings key for a base URL exists): `GOOGLE_GEMINI_BASE_URL`+`GEMINI_API_KEY`; omp ("Oh My Pi", a Pi fork — selectable, not a default) → the GLOBAL in-VM `~/.omp/agent/models.yml` (YAML, KEYLESS — the provider `apiKey` NAMES the `AIP_GATEWAY_KEY` env var, resolved at runtime; `openai-models-list` DISCOVERY, so omp lists exactly the served models live each launch, NO static list to refresh) + `<project>/.omp/config.yml` (provider order + seed-then-remember `modelRoles.default`). **Per-agent auth mode** (`config.AgentConfig.AuthModes`, `agent.auth_modes` in config.yaml, keyed by CLI): the three CLIs with a first-party subscription login — **claude-code, codex, gemini** (`config.OAuthCapableCLIs()`) — each record `api-key` (DEFAULT — route through the gateway with the scoped virtual key, so the tool firewall + secret masking apply; NOT Headroom-wrapped) or `oauth` (the CLI's OWN subscription login, talking DIRECTLY to the provider, BYPASSING the gateway and its guardrails). opencode/pi/omp have no subscription and are ALWAYS gateway/api-key (never asked, never oauth). **copilot** (GitHub Copilot CLI) is a FORCED-OAUTH CLI (`config.ForcedOAuthCLIs()`, `config.IsOAuthEligible`): it is OAuth-only / gateway-INCAPABLE — it authenticates natively to GitHub (device-flow login, or a GH_TOKEN/GITHUB_TOKEN PAT) and talks DIRECTLY to GitHub's Copilot backend — so it has NO api-key mode, is NEVER offered an auth-mode choice (the create wizard/`--auth-mode` skip it; `--auth-mode copilot=api-key` is rejected exit 2), is recorded as `oauth` AUTOMATICALLY by `Scaffold` when selected, and `AgentConfig.AuthMode("copilot")` always returns `oauth` regardless of the map. It gets NO gateway env and NO platform-written on-disk config (it manages its own `~/.copilot`); it IS Headroom-wrappable (`HeadroomWrapName("copilot")="copilot"` → `alias copilot='headroom wrap copilot'`), its `~/.copilot` cred dir is symlinked to `/persist` (`linkAgentStateDirs`), its provider egress domains (`api.githubcopilot.com`/`api.github.com`/`github.com`) are allow-listed by `Scaffold`, and it is a Graphify platform (`--platform copilot`). `ai create` WARNS that its traffic bypasses the firewall/masking/content-egress-audit (like any oauth agent). Chosen at `ai create` (the `--auth-mode cli=mode` flag / per-agent wizard steps / the TUI create phase) and persisted for the selected+OAuth-capable CLIs. At workspace start (`registerAgentProviders` via `oauthAgentList`) an oauth agent's gateway env is OMITTED (`AgentEnvScript` drops `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` for oauth claude-code and `GOOGLE_GEMINI_BASE_URL`/`GEMINI_API_KEY` for oauth gemini; the shared `AIP_GATEWAY_KEY` still exports for opencode/pi), its on-disk config drops the gateway route (oauth claude-code's `.claude/settings.json` env block is emptied via `MergeClaudeSettingsOAuth`; oauth codex's `.codex/config.toml` is the `CodexConfigOAuth` variant — `forced_login_method="chatgpt"` + `cli_auth_credentials_store="file"`, NO gateway provider block), and — because Headroom `wrap` supports `claude`+`codex` but NOT `gemini` — oauth claude-code/codex get an `alias <cli>='headroom wrap <cli>'` (`ShellAliases` is fed ONLY the oauth-wrappable set; api-key agents route through the gateway where Headroom already sits, so they get NO alias) while oauth gemini goes direct with no wrap/alias. Each oauth agent's NATIVE-login credential dir is persisted across restarts — `linkAgentStateDirs` symlinks `~/.claude`/`~/.codex`/`~/.gemini` into `/persist` for the oauth agents. At CREATE, `Scaffold` also allow-lists each oauth agent's provider egress domains (`agentcfg.OAuthProviderDomains` — claude-code→api.anthropic.com; codex→api.openai.com/chatgpt.com/auth.openai.com; gemini→generativelanguage.googleapis.com/oauth2.googleapis.com/accounts.google.com/cloudcode-pa.googleapis.com) into `network.allow_host_services` so the agent reaches its provider under `deny`. The HARD invariant holds: the scoped virtual key is still never on host disk — oauth agents simply don't get it. Routing an OAuth/subscription agent through the gateway WITH the firewall enforced remains blocked upstream (docs/deferred/oauth-agent-firewall-via-gateway.md); `ai create` WARNS for each oauth agent that its traffic bypasses the firewall/masking/content-egress-audit. The old `.ai-platform/agents/` keyless-template layer is RETIRED (ensureAgentTemplates/readAgentTemplate/writeAgentTemplates/OpenCodeTemplate/PiTemplate + the *TemplateFile consts are GONE). **HARD SECURITY INVARIANT: the scoped virtual key (and any real key) is NEVER written to host disk** — it lives ONLY in the in-VM agent env file `~/.config/aip/agent-env.sh` (`AgentEnvScript`, written via `Sandbox.WriteFile`, sourced by every session), which exports `AIP_GATEWAY_KEY` (opencode/pi/codex), `ANTHROPIC_AUTH_TOKEN` (claude-code), `GEMINI_API_KEY`/`GOOGLE_GEMINI_BASE_URL` (gemini) + `OPENCODE_CONFIG`; the on-disk configs are all keyless (`{env:}`/`$VAR`/codex `env_key`/claude exported token). The env file is sourced by every session — the agent-launch command wraps each CLI in `bash -lc 'source <env>; exec <cli>'` (`wrapWithAgentEnv`) and a managed `~/.bash_profile` (`agentcfg.BashProfile`) sources it for interactive `ai shell`/`ai attach` AND falls back to `TERM=xterm-256color` when the host terminal's `$TERM` has no in-VM terminfo entry (Ghostty's `xterm-ghostty`, kitty, …) — inside a session tmux's `tmux-256color` default already applies, so this covers the pre-tmux/non-tmux exec path. At start the platform DEEP-MERGES (`MergeOpenCodeConfig`/`MergePiSettings`/`MergeClaudeSettings` — generated managed block WINS, user's other keys survive) the dynamic values over any EXISTING on-disk config, so user edits survive restart; pi's global models.json is written whole (not merged) and codex's project block is fully managed (rewritten each start). A test asserts the on-disk configs contain no key. **Shared resource pool + symlinks (`linkSharedResources`):** `<project>/.ai-platform/{agents,skills,prompts,projects}` is a shared pool; at start (BEFORE Graphify registration, so Graphify's per-CLI skill files land in the pool) each pool is symlinked (relative) into each INSTALLED CLI's real dir — skills → `.opencode/skills`/`.claude/skills`/`.pi/skills`/`.omp/skills`; agents → `.opencode/agents`/`.claude/agents`/`.omp/agents` (omp reads its OWN native `.omp/agents` for task-agents and deliberately SKIPS `.claude/agents`, so it needs its own link); prompts → `.opencode/commands`/`.claude/commands`/`.gemini/commands`/`.pi/prompts`/`.omp/commands` (kinds a CLI lacks are skipped — codex/gemini have no skills/agents); Caveman is installed into the pool at workspace start by `registerCaveman` (mirrored from opencode's native install), so `<project>/.ai-platform/skills/caveman/SKILL.md` appears there AFTER the first start and is thereby shared to every skills-capable client (its presence is what `ai context status` reports as caveman-installed). The in-VM agent model picker is EXACTLY the models the LiteLLM gateway currently SERVES (its live DB-backed models), sourced via the injected `workspace.ServedModels` (wired to `litellm.KeyManager.ListModels`) and built by `Manager.pickerModels` at workspace start — the served names are sorted, the list DEGRADES GRACEFULLY to EMPTY when the gateway is unreachable (never fails the start). **The served-model LIST is (re)written on EVERY start/restart AND on shell/agent ATTACH** (`workspace.writeModelListConfigs`, called by `registerAgentProviders` at start and by `launchTmuxSession` via `refreshAgentModels` on attach), so a model added/removed with `ai models`/`ai keys` appears in the next session WITHOUT a full restart — opencode's `provider.<id>.models` map is REPLACED wholesale (models removed upstream disappear; all OTHER user keys survive the merge) and pi's global `~/.pi/agent/models.json` is rewritten whole. Only **opencode + pi** carry a refreshable list (codex/gemini/claude name any served model per request). An EMPTY served list (gateway down) LEAVES the existing lists UNTOUCHED — a transient outage never wipes them. The attach refresh is LIST-ONLY: it never rotates the scoped key, rebuilds the env, or re-seeds. The workspace DEFAULT model follows a SEED-THEN-REMEMBER policy: the model chosen at setup (`agent.graphify_model` → `ollama/<model>`) is SEEDED as every CLI's default on the FIRST start ONLY (guarded by a `<project>/.ai-platform/.agent-default-seeded` marker); Open WebUI is no longer a host service — it now runs as a **per-workspace in-VM app** (`internal/apps`); **Odysseus has been removed from the platform entirely** (no host containers, no docker-socket mount). There are currently NO optional host services — the optional MECHANISM is retained (empty set) for future use. **`aip-proxy` (nginx) is the SOLE host entry point to the service tier: every other service container is INTERNAL-ONLY on `aip-net` (reached by name) — only nginx publishes ports to the host** (besides the loopback-only `aip-litellm-db` :5442 and `aip-dns` :15353). The services: `aip-dns` (CoreDNS egress-audit resolver, bound to host loopback `127.0.0.1:15353/udp`; microVMs use it via `--dns-nameserver`; it forwards upstream to the CONTAINER'S OWN `/etc/resolv.conf` — Docker's embedded DNS, which inherits the host resolver — NOT hardcoded public resolvers like 1.1.1.1/8.8.8.8, so it still resolves on restricted/corporate networks that block direct external DNS), `aip-ollama` (required local models, INTERNAL-ONLY — no host publish — reached by name at `http://aip-ollama:11434` and from the host via nginx's `/ollama` route; Detection (`internal/runtime` + `internal/sandbox`) is parameterized by `GOOS/GOARCH` + a `Prober` so it tests on any host; missing deps → exit 3, missing rootless/virtualization → exit 4. macOS requires **Apple Silicon** (no Intel). **Deployment roles** (chosen interactively by `ai setup`, or `--mode`, persisted as `role:` in `runtime.yaml`): **standalone** (default — full service tier + workspaces here; shared services bind **127.0.0.1**), **server** (only the service tier, bound **0.0.0.0** for remote clients, no workspaces — preflight needs only docker + rootless), **client** (only workspaces; routes to a remote `--server` address held in `ai_platform_host`, skips the local reconcile — preflight needs only msb + virtualization). Per-project workspace egress is declared via `ai network` (modes public[default,allow-outbound]/deny/unrestricted, allowed host services incl. domains + `*.suffix`, published ports, stored in `config.yaml`) and applied as Microsandbox net-rules (`egress.MsbNetworkArgs`; the default-deny fallthrough still blocks private ranges under `public`, and the always-on host-gateway + DNS allow rules stay) at workspace create. Host-reaching rules MUST target msb's `host` GROUP token (`allow:egress@host:tcp:<port>`), NOT the `host.microsandbox.internal` NAME: only the `host` group engages msb's host-forwarding — a host-NAME target lets the guest connect to the msb gateway but is never forwarded to the host service (empty reply, verified live). So the LOCAL gateway rule + the `gateway`/empty host-service allow-list entries + the always-on DNS pair (`Rule::allow_dns()` = `host:udp:53` + `host:tcp:53`, required so DNS resolves under default-deny) all use the `host` group; a remote gateway (client mode) and explicit domain/IP host-services stay verbatim. **Model gateway wiring** (`ai gateway show|set|clear`, `internal/cli/gateway.go`): the machine-wide `ai_platform_host` in `runtime.yaml` (set by `ai gateway set <host[:port]>` or `ai setup --mode client --server`) selects which gateway every workspace microVM on this host routes through. `internal/workspace` derives it at start via `runtime.ResolveGateway(Info.HostAddress())` — bare host or `host:port`, default port 18787; empty → `host.microsandbox.internal:18787` (standalone/local) — and uses the resolved `http://<host>:<port>/v1` for the agent provider configs' `base_url` and the resolved `<host>:<port>` for `MsbNetworkArgs(network, gatewayHost, gatewayPort)`'s always-on egress allow rule. `ai gateway` exits 3 (no runtime.yaml — run `ai setup`), 2 (invalid address), 4 (persist/read failure). **Platform base domain** (`ai domain [name]`, `internal/cli/domain.go`): the machine-wide `domain` field in `runtime.yaml` is the base domain the nginx UI subdomains hang off — `litellm.<domain>` + `valkey.<domain>` — defaulting to `aip.local` (`runtime.DefaultDomain`, resolved via `Info.ResolveDomain()`/`runtime.ResolveDomain`) for local/standalone and overridden in server mode. `ai domain` with no arg SHOWS the resolved domain; with a name it VALIDATES a lowercase DNS hostname (labels of `[a-z0-9-]`, no scheme/path/whitespace, no leading/trailing dot) and persists it, mirroring `ai gateway`'s load-modify-save + exit codes (3 no runtime.yaml, 2 invalid, 4 persist/read). This `domain` is wired into the nginx UI vhost + the standalone `/etc/hosts` block (see the Dual runtime model above).

**Model catalogue is global, DB-backed, and catalog-driven.** Models are registered in LiteLLM's Postgres-backed model store (`general_settings.store_model_in_db: true`) — the rendered `config.yaml` has NO `model_list`, NO named aliases, NO per-provider wildcards, and NO default model (`litellm.DefaultRouting()` now returns the ZERO `Routing` — empty `Default`, empty `Aliases`). The model set is driven by the **models.dev catalog** (`internal/catalog`, fetched as JSON from `models.dev/catalog.json` and persisted as YAML to `~/.ai-platform/cache/catalog.yaml` at `ai setup` and on the Cloud Models tab `r` key — a legacy `catalog.json` copy is one-shot converted to YAML; `catalog.LoadOrFetchStatus` reports the data `Source` fresh-vs-cached so the UI can message availability): adding a provider API key via `ai keys` syncs that provider's catalog models INTO the DB, removing it syncs them OUT (`litellm.SyncModels`; the catalog-id→LiteLLM-prefix map is e.g. `google`→`gemini`, and the public `model_name` registered is the catalog id verbatim — but `SyncModels` NEVER deletes `ollama/*` models: those are owned solely by `ai models pull`/`rm`, so a cloud-key resync run with an empty/unknown Ollama list (e.g. the daemon momentarily unreachable) can't wipe registered local models), while Ollama models are registered/unregistered as DB-backed models by `ai models pull`/`rm` (`litellm.RegisterOllamaModel`/`UnregisterOllamaModel`, public `model_name` `ollama/<name>`). The in-workspace agent names any served model per request and LiteLLM routes it (real provider keys live in LiteLLM; the agent authenticates to the gateway with a scoped virtual key, Ollama needs none) — there is **no per-project model config**. LiteLLM's generated config renders a **user-selected guardrail set** — chosen at `ai setup` (a multi-select picker, or the `--guardrails` flag; persisted machine-wide in `runtime.yaml` `guardrails:`, resolved for the render by `reconcileGuardrails`/`setup.ResolveGuardrails`, defaulting to `litellm.DefaultGuardrails()` when unset). The selectable guardrails (catalog: `litellm.Guardrails`) are: **headroom** (input compression — the ONLY one **default-on**), **secret-masking** (Presidio), **hide-secrets** (detect-secrets), and **tool-firewall** (`tool_permission`). Only the ENABLED guardrails are rendered — an unselected one is omitted entirely (never referencing a backend that isn't running) — and each rendered guardrail is `default_on: true`, so a client request cannot opt out of an enabled one. **The Presidio containers (`aip-presidio-*`) are pulled + started ONLY when `secret-masking` is enabled** (`presidioSelected` gates `requiredImages`/`PullImages`, the reconcile's `ensurePresidio`, and the Control "all" path; Status reports Presidio "disabled" when off) — no point consuming resources for a guardrail that isn't rendered. All guardrails are scoped to **secrets/credentials, not general PII**: `secret-masking` expands to `presidio-secrets-input` (pre_call) + `presidio-secrets-output` (post_call), masking only financial/identity secrets (CREDIT_CARD, US_SSN, US_BANK_NUMBER, IBAN_CODE, CRYPTO — see `secretEntities`); `hide-secrets` is LiteLLM's in-process detect-secrets for API keys/tokens. Masking general PII (names, places, emails) was deliberately removed — it corrupted ordinary coding prompts. The **tool firewall** (`guardrail: tool_permission`, `mode: post_call`) DENIES destructive command tool-calls (`git push --force`, `rm -rf`, `terraform destroy`, `kubectl delete`, … — `destructiveCommandPatterns` in `internal/litellm`) — for coding agents the bigger risk is destructive tool execution, not prompt content. The in-process **prompt-injection** callback (`detect_prompt_injection`) was REMOVED — like the unmaintained **LLM Guard** (also removed) it false-positived on ordinary coding/Ollama traffic; Guardrails AI (needs a Hub token + per-guard install) remains **deliberately deferred**. Because every enabled guardrail is default_on and all routes (cloud included) traverse the proxy, cloud calls cannot bypass an enabled guardrail. Registering a model ≠ installing it (an Ollama model still needs pulling — via `ai models pull`; a cloud model still needs its key). **Ollama model management** is `ai models` (`internal/cli/models.go`+`models_local.go`, over the injected `ollama.Client`/`litellm.Client`): `status` (LiteLLM health + the served/provider view sourced LIVE from the gateway — `/model/info` → `/v1/models`, not from any aliases — plus Ollama connectivity), `test [model]` (round-trips a model through the gateway), `list` (installed local models), `popular` (the live installable library), `pull [name...]` (downloads into the local Ollama store — names/`--json` pull each ref in turn, rendering a live download progress bar per ref from Ollama's streamed total/completed frames via `ui.ProgressBar` (`ui.NewProgressBar`, `\r`-overwriting so it also renders in the `ai ui` embedded terminal); a TTY with no args checks off library `name:tag` refs + an optional custom-ref entry; re-pulling updates, there is no separate update verb), `rm [name]` (removes a local model), and `show <name>` (model metadata). The installable library is **scraped LIVE from ollama.com** (`internal/ollama/library.go` — `ollama.Library()` GETs the `https://ollama.com/library` index for every model name + description, then fetches each model's `https://ollama.com/library/<model>/tags` table for the per-variant `size`/`context`/`input`, bounded by `tagFetchConcurrency`; a per-model tag-page failure keeps the model with empty tags rather than failing the whole scrape; each model's `RepoURL` is DERIVED as `https://ollama.com/library/<name>`). `LibraryModel.Tags` is now `[]LibraryTag{Name,Size,Context,Input}` (Name is the SHORT tag). The result is cached as YAML at `~/.ai-platform/cache/ollama-models.yaml`, falling back to that cache when ollama.com is unreachable (`LoadOrFetchLibrary` reports `Source` fresh-vs-cached; the old third-party `ollama-models.zwz.workers.dev` JSON endpoint was stale and is GONE). There is NO bundled `models.yaml` and no offline fallback set — `ai models popular` shows each model's default-tag SIZE / CONTEXT / INPUT (dashes when the table omits them) and its refs are `name:tag`. The `ai ui` TUI splits models into a **Local Models** tab (`internal/tui/views/localmodels.go`) and a **Cloud Models** tab (`internal/tui/views/cloudmodels.go`) — there is no single combined "Models" tab; the top-level view order is Services · Workspaces · Local Models · Cloud Models · API Keys · Settings. Local Models lists an **Installed** section (library models with ≥1 pulled tag, plus installed customs) + an **Installable** section (the rest of the live library), rendered as a custom **viewport-windowed list** (NOT a bubbles table, so the section headers can be styled) showing **NAME · DESCRIPTION only — there is no TAGS column** (tags live solely in the per-model drill-down), with a per-model **tag drill-down** (`enter`; each tag row shows its scraped `size · context · input`) to space-select 1+ NOT-installed tags then `enter`/`p` to pull (emitting `ModelsPullRequestedMsg{Refs}` → `ai models pull <refs…>`), `d` to remove an installed tag, `t` to test one (and `enter` on an installed tag opens its `/api/show` detail) — list keys `enter` manage tags · `t` test · `d` remove · `r` refresh (which ALSO registers the installed Ollama models with the gateway — `RegisterOllamaModels`, ADD-only — so refreshing recovers any local model still in Ollama but missing from LiteLLM); Cloud Models lists the models.dev catalog ⨯ the gateway's live registered set in a bubbles MODEL · PROVIDER · STATUS · CONTEXT table, showing ONLY models for keyed/registered providers (it EXCLUDES local `ollama/<name>` models) — `enter` details · `t` test (registered) · `r` refresh catalog + resync (provider keys stay in the API Keys tab — PROVIDER · NAME · KEY? · MODELS; `a` add · `e` edit (overwrite) · `d` delete · `r` refresh, `esc` backs out of the add/edit overlay, and the key VALUE never enters the view). When models.dev OR the ollama library endpoint is unreachable, each view uses its cached copy and flashes a source-availability message; with no cache it shows the message + an empty section. `ai services start|stop|restart` manage the whole platform container set (ollama, presidio [only when the `secret-masking` guardrail is enabled], valkey, redisinsight, headroom, litellm, proxy, dns); `ai services update [service]` (and the `p` key in the TUI Services DETAIL, routed through the embedded terminal overlay) force-RE-PULLS the latest images (`Services.UpdateImages` — unlike the first-run `PullImages` it does NOT skip already-present images, so a moved `latest` tag is refreshed) then restarts the target so its container is recreated against the new image (`setup.UpdateService`); ClawPatrol is gone and there is no native service to manage. **`ai services compose`** writes a DEBUG-ONLY `~/.ai-platform/docker-compose.yml` (`setup.ServicesComposeYAML`/`WriteComposeFile`) mirroring the service-tier topology — it is NOT the launcher (the per-container `ensure*` reconcile still owns startup + keeps docker/podman parity); it is generated from the SAME consts/helpers (`containerImage`, `platformNetwork`, the volume/config paths, `ollamaEnvPairs`) so it stays in sync, with the LiteLLM secrets emitted in compose PASSTHROUGH form (bare `UI_PASSWORD`/`LITELLM_MASTER_KEY`/`LITELLM_SALT_KEY`, no values) so they never hit disk. A developer brings the SAME stack up under compose's tooling for debugging (`ai services stop && docker compose -f … up -d`, then `logs -f`/`ps`/`restart`). The LiteLLM admin UI is secured with `UI_USERNAME`/`UI_PASSWORD`/`LITELLM_MASTER_KEY` passed by **env passthrough** (values never in argv/config/disk). **Role-based UI-auth policy** (`runtime.RequireUIAuth(role)`, true ONLY for `server`): standalone/client run OPEN — `ai setup` does NOT prompt for a LiteLLM password; a server REQUIRES a password (`ai setup` loops on a TTY until non-empty, generates one non-interactively rather than leave the gateway open). (The in-VM Open WebUI app sets its own `WEBUI_AUTH`; the removed host Open WebUI/Odysseus services no longer factor in here.) A standalone user opts into a password later via **`ai litellm password`** (`internal/cli/litellm.go` — prompts hidden, reuses the running master key else mints one, `RelaunchLiteLLMWithAuth`; exit 3 if not set up / client / gateway down, 2 on bad/empty/non-TTY input, 4 on relaunch failure). Both `ai setup` and `ai litellm password` then OFFER to persist `UI_PASSWORD`+`LITELLM_MASTER_KEY` to **`~/.ai-platform/.ai-platform.env`** (`internal/envfile` — opt-in **0600** `export KEY='VALUE'` file, auto-loaded at `ai` startup in `root.go` `PersistentPreRun` before `ui.Apply`; existing env WINS, file only fills gaps) so they survive restarts with no shell-rc edit; on decline / non-TTY the manual `export …` block is printed.

**The CLI surface is FLAT: workspace management lives in top-level verbs** (CLI §3/§4) — `ai create`/`ai list`/`ai delete` (create/list/delete a workspace; **`ai delete` is the single removal verb — `destroy` is now an ALIAS of it**, not a separate VM-only teardown: a plain delete tears down the microVM, removes the project's `.ai-platform` dir + overlay, and de-registers it from `projects.yaml`, keeping the user's OTHER files; `--purge` removes the whole project directory) and `ai start`/`ai stop`/`ai restart`/`ai exec`/`ai shell`/`ai agent`/`ai attach`/`ai sessions`/`ai apps` (microVM lifecycle + sessions + in-VM apps), each taking an OPTIONAL `[name]` resolved via `resolveProjectName` (explicit name → `--project` → cwd workspace). The grouped `ai workspace …` / `ai project …` commands were **removed** — the flat verbs are the only surface (their shared RunE bodies live in `internal/cli/workspace.go` as `workspace*RunE`, plus the `newCreateCmd`/`newListCmd`/`newDeleteCmd` constructors in `project.go`; the envelope `command` keys stay `workspace.*`/`project.*`). The user-facing noun is **"workspace"** in all help/messages/TUI labels, but internal package/type/field names (`internal/project`, `project.Entry`, `state.Project`, `views.Projects`/`ProjectsHub`) and JSON data keys (`{"project": …}`) keep "project" for stability. NB: `ai doctor [name]` is **consolidated** — it always reports platform health + every service-tier service (ollama, presidio, litellm, headroom, proxy, dns), and ADDITIONALLY the workspace-runtime checks (rootless + virtualization) when inside a workspace dir (cwd/ancestor) or given `[name]`; there is no separate `ai workspace doctor`. It always exits 0 with a report (per-check status conveys health).

**`ai create` is an in-process `charmbracelet/huh` wizard** (CLI §3.1): workspace name + **location**, OS (`debian-trixie`/`debian-bookworm`/`ubuntu`/`alma`), agent CLIs (multi-select: `opencode`/`pi`/`omp`/`claude-code`/`codex`/`gemini`/`copilot`/`openclaw`/`hermes` — `opencode` (default tool) and `pi` are installed by default, both wired to LiteLLM; `omp` ["Oh My Pi", a Pi fork], `openclaw` [github.com/openclaw/openclaw, npm] and `hermes` [NousResearch/hermes-agent, curl-installer] are selectable and, when chosen, wired to LiteLLM the same gateway/api-key way (ALWAYS gateway, NEVER OAuth — like opencode/pi/omp): openclaw → GLOBAL in-VM `~/.openclaw/openclaw.json` (`aip-gateway` provider, `apiKey:"${AIP_GATEWAY_KEY}"`, `api:openai-completions`, served models enumerated + refreshed on start/attach like opencode/pi via `writeModelListConfigs`), hermes → GLOBAL in-VM `~/.hermes/config.yaml` (`aip-gateway` provider, `key_env:AIP_GATEWAY_KEY`, endpoint model-discovery like omp, `external_dirs` → the shared skills pool); both KEYLESS (`agentcfg.OpenClawConfig`/`HermesConfig`, written via `Sandbox.WriteFile`), Caveman-detectable (`cavemanOnlyAgent` → native `--only` install), inherit Graphify's skill via the pool (NOT in `graphifyPlatformFlag`, same as omp), and get Headroom input-compression automatically at the gateway (the LiteLLM `pre_call` guardrail — NO wrap alias); `copilot` [GitHub Copilot CLI] is selectable and is FORCED-OAUTH / gateway-INCAPABLE — it authenticates natively to GitHub and talks DIRECTLY to GitHub's Copilot backend, so it never routes through the gateway, gets no api-key/oauth choice, is Headroom-wrapped, has its `~/.copilot` cred dir persisted, and is Graphify-registered via `--platform copilot`), default agent CLI, software stacks (`go`/`rust`/`java`/`maven`/`deno` — **neither Python NOR Node is a stack** (the no-op node/python snippets were removed): Node.js (pinned Node 24 LTS) and the latest **Python 3**, **uv** (Astral's package/tool manager), and **Graphify** (`graphifyy`, installed via `uv tool install "graphifyy[…extras]"` — all extras except the region/DB-specific chinese/azure/bedrock/falkordb/neo4j/leiden/dm) are baked into every OS base by default (uv + Graphify install onto the workspace user's `~/.local/bin`). **rtk** (`github.com/rtk-ai/rtk`, "Rust Token Killer") is likewise baked into every OS base for the workspace user via its official `install.sh` (prebuilt aarch64 Linux binary → `~/.local/bin`, on PATH, no root) — a CLI proxy that compresses common dev-command output; Claude Code's rtk PreToolUse hook (added by the user's `rtk init`, not by the platform) shells out to `rtk`, so the binary must be present or the hook fails `rtk: command not found` (exit 127); installed via `install.sh`, NEVER `cargo install rtk` (crates.io name collision). Each selected agent CLI registers Graphify with itself at WORKSPACE START (NOT image build) via `graphify install --project [--platform <cli>]` run in `~/project` (`Manager.registerGraphify`, iterating `config.Agent.Tools`) — it must run at runtime because `--project` writes project-scoped skill/plugin/hook files (e.g. opencode's `.opencode/plugins/graphify.js`, `AGENTS.md`) into the bind-mounted project dir, which does not exist at build; Graphify writes into the SAME per-CLI project dirs the platform manages (e.g. `.opencode/`), but distinct files — the platform owns `opencode.json`/`models.json`/`settings.json`/`config.toml`, Graphify owns its plugin/skill/hook files, and its skill files land in the shared pool via the symlinks (created BEFORE registration) — so no clobber; it's config-only/offline/best-effort. It runs ONCE per project, guarded by a marker file `~/project/.ai-platform/.graphify-installed` so it does NOT re-run and clobber user edits on every restart. Additionally, when the project is a **git repo** (a `.git` dir present), `registerGraphify` also runs `graphify hook install` ONCE — guarded by its OWN marker `~/project/.ai-platform/.graphify-hook-installed`, re-checked each start so a project that becomes a git repo AFTER the first start still gets the hook exactly once (both steps run in one `sh -lc` exec in `~/project`, best-effort). claude-code uses the default platform (no `--platform`); codex/gemini/opencode/pi/copilot pass `--platform <cli>` (those six agent CLIs ARE Graphify platforms — `graphifyPlatformFlag`). **omp is NOT in `graphifyPlatformFlag`** — an unverified `graphify --platform omp` would fail and poison the once-guarded install chain (aborting it before the marker is touched, so it retries every start); omp instead inherits Graphify's skill (and Caveman) via the shared resource pool symlinked into `.omp/`. Graphify's headless LLM backend is an Ollama model chosen AT CREATE — the wizard's optional model+tag select (from the cached Ollama library, mirroring the Models page) or the `--graphify-model` flag; blank = none — stored as `agent.graphify_model` in `config.yaml` (`config.AgentConfig.GraphifyModel`, carried via `project.Spec.GraphifyModel`), pulled into the local Ollama store + registered in LiteLLM if absent (best-effort — a pull failure is a create WARNING, not a failure: `pullGraphifyModelIfAbsent`), and routed at workspace start through the gateway as `ollama/<model>` via `agentcfg.AgentEnvScript`'s `OPENAI_BASE_URL`/`OPENAI_API_KEY`/`OPENAI_MODEL` exports (so `graphify --backend openai` goes nginx → LiteLLM → Ollama, never direct; no real provider key). Each workspace also gets a per-project `~/project/.venv-msb` virtualenv created at start by `Manager.ensureVenv`; the venv lives in the bind-mounted project dir so it is ONE directory visible on host+guest, but it is a Linux venv usable only IN the sandbox — a venv is not portable across the macOS host and the Linux guest), in-VM apps, and the **resource/ports** group (**vCPUs**, **memory**, **published ports**) are picked across the wizard's groups. Every input also has a flag (`--name`/`--os`/`--agents`/`--stacks`/`--apps`/`--cpus`/`--memory`/`--ports`/`--location`/`--idle-timeout`/`--graphify-model`/`--shell`); the create inputs are bundled in a `createFlags` struct (`seedSpec`/`specFromFlags`/`validateProvidedCreateFlags`). The deterministic in-process work (validate/cap resources, scaffold `.ai-platform/`, seed contextopt defaults, best-effort Graphify-model pull) lives in the SHARED **`internal/create`** package — `create.Execute(spec, now)` — imported by BOTH `ai create` (the CLI) and the `ai ui` TUI create wizard, so both paths behave identically without a subprocess; the selectable option lists (`SupportedOSes`/`SupportedStacks`/`SupportedAgentCLIs`/`SupportedApps`) also live there (the TUI can't import `internal/cli`). On a TTY the flags **pre-seed** the wizard (which always shows — flags are never required there), while under `--json` or no TTY the spec is built straight from the flags with no prompt and `--os` is **required** (a missing `--os` exits 2). **Resources are host-capped**: `--cpus` ≤ host logical CPUs (`sysinfo.CPUs()`), `--memory` ≤ host RAM (`sysinfo.MemoryMiB()` — darwin `hw.memsize` / linux `/proc/meminfo`); an over-host request exits 2. These write `workspace.cpu_limit`/`workspace.memory_limit` and `network.publish_ports` (ports are `PORT` or `HOST:GUEST`, Docker-style host-first). The **location** (`--location`, default cwd) is **created if missing** and may NOT be — or be nested inside — an existing workspace (`project.nearestAncestorProject` walks ancestors for a `.ai-platform/project.yaml`; violation exits 2); the wizard location field offers path autocompletion (`huh` `SuggestionsFunc`) and the flag shell dir-completion (`MarkFlagDirname`). With no explicit `--location`, if the cwd is already a workspace it **attaches** instead. The microVM is created through the **Microsandbox Go SDK** (the default `internal/workspace` SDK backend); the platform runs **no git** (VCS is out of scope). `--dry-run` emits the side-effect-free action plan. The command itself uses no PTY; automation drives it through a pseudo-terminal (`creack/pty`) only via the acceptance harness in `test/acceptance` (§1.4).

## Conventions

- **Commands prompt on a TTY** (CLI §1.8), via the shared helpers in `internal/cli/prompt.go` (`interactive`/`runForm`/`promptText`/`promptSecret`/`promptChoice`/`promptMultiChoice`, all built on `charmbracelet/huh`). On a terminal the prompt ALWAYS shows, **pre-seeded** with any value given as an arg/flag (the user confirms/edits — the value never silently bypasses the TUI); only under `--json`/no-TTY is a provided value used directly, with a missing required value erroring (exit 2) so automation stays scriptable. Two exceptions: a **hidden credential value** (`ai keys add --value/--stdin`) is used directly even on a TTY (a hidden field can't show a seed), and `ai services start|stop|restart` act directly on an explicit name/`all` and only show the checkbox with no arg. Known option sets are shown as selects/checkboxes. **All of a command's prompts must share ONE `runForm`** so the user can navigate back between them — never chain separate prompt calls. The TUI look-and-feel is **theme-selectable**: `internal/ui` owns a registry of named themes (huh built-ins `default`/`dracula`/`catppuccin`/`base16`/`monochrome` plus custom palettes in `custom_themes.go` — `orange`/`synthwave`/`cyberpunk`/`tokyo-night`/`nord`/`gruvbox`/`onedark`/…, each wrapping a huh theme + heading accent; `ui.TableStyles()` themes the `ai ui` tables with the active accent), persisted per host in `~/.ai-platform/config/ui.yaml` and applied once at startup (root `PersistentPreRun` → `ui.Apply(ui.LoadThemeName())`); `ai theme [name]` shows/selects it (the semantic status colours stay fixed across themes).
- **No single-character variable names anywhere** — including method receivers and loop vars (`store`, `emitter`, `prober`, `entry`, `value`, …). Self-documenting names over Go's terse-receiver convention. The one kept exception is the test handle `t *testing.T`.
- **Every YAML file the platform generates uses the `.yaml` extension, never `.yml`** — config/runtime/versions/catalog/ollama-models/ui/profile/project state, the `ai services compose` artifact (`~/.ai-platform/docker-compose.yaml`), all of it. The ONLY exception is a filename an EXTERNAL tool mandates: omp reads `~/.omp/agent/models.yml` + `<project>/.omp/config.yml` (documented as `.yml`, not a name we choose), so those stay `.yml`. When a new external tool dictates a `.yml` path, match it and note the exception at the write site; otherwise `.yaml`.
- **Provider API keys never touch platform disk.** Keys flow straight to the LiteLLM credential store (encrypted at rest by `LITELLM_SALT_KEY`) via `litellm.KeyManager` (`SetCredential`/`DeleteCredential`/`ListCredentials`), which `ai keys` fronts; `ListCredentials` returns names + provider prefixes only (never values), so listings can't leak. `ai keys` is catalog-driven (`internal/catalog`, models.dev): a key is keyed per LiteLLM-routable provider, and `add`/`remove` sync that provider's catalog models into/out of the gateway (`litellm.SyncModels`). It **replaced** the former `ai secrets` command and the `internal/secrets` package.
- **Parallelize with subagents + git worktrees where the work is disjoint — but never at the cost of merge chaos.** When a task decomposes into independent units that touch *different* files, prefer launching multiple subagents in parallel, each in its own git worktree (`isolation: worktree`), then integrate by pulling each branch's files (`git checkout <branch> -- <files>`). Do NOT parallelize units that edit the **same** file (notably `internal/setup/setup_real.go`, `internal/tui/tui.go`) — sequence those instead. The rule that keeps integration clean: each agent owns a **disjoint file set**, and the parent does any shared wiring (e.g. registering new views in `tui.go`) itself. If you can't partition the work into disjoint file sets, do it single-threaded.
- Commit messages must not include AI-attribution trailers (no `Co-Authored-By` for the assistant). Commit only when asked; the work lives on a feature branch off `main`.
