# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, and any tool that reads `AGENTS.md`) when working with code in this repository.

## What this is

The `ai` CLI — the single control-plane binary for the **AI Development Platform**: reproducible AI dev environments where each agent-CLI session is sandboxed on the **host** by **[nono](https://nono.sh)** — a kernel-capability sandboxing tool (Landlock LSM on Linux, Seatbelt on macOS), **not a virtual machine**. This is a deliberate, accepted security-model change from the platform's previous Microsandbox-microVM design: nono is same-kernel process sandboxing, not hardware/VM isolation, and it has no Apple-Silicon-only / hypervisor requirement (any host the `nono` binary runs on can use it). There is no guest OS, no OCI image to build, no Dockerfile per project, and no persistent boot: a "workspace" is just a registered project directory (`internal/project`) plus a generated nono profile — a JSON capability grant written fresh before every launch to `<project>/.ai-platform/nono-profile-<cli>.json` (or `nono-profile-shell.json` for a bare shell) — scoping filesystem access to the project directory and declaring a network policy. Every `ai agent <cli>`/`ai shell` invocation is its own ephemeral nono session (`nono run --detached`, `nono shell`, `nono attach`, `nono stop`, `nono ps --json`, `nono inspect --json`), started/listed/reattached/stopped independently via nono's own session lifecycle — there is no restart-to-apply-config step, since the profile (and the per-CLI config file) is regenerated on every launch. The model path is otherwise unchanged: agent → host **Caddy** gateway (plain loopback `http://127.0.0.1:18787`, or a remote gateway set machine-wide with `ai gateway set`) → **LiteLLM** routing (with a **user-selectable guardrail set** chosen at `ai setup` — the **Headroom** input-compression `pre_call` guardrail is the only one ON by default; **Presidio** secret-masking, detect-secrets, and the destructive-command tool-firewall are opt-in — each enabled one applied in-process on every request; the Presidio containers start only when secret-masking is selected) → a **local-inference backend** — **omlx** ([jundot/omlx](https://github.com/jundot/omlx), the platform's REQUIRED local runtime, **macOS on Apple Silicon only, with no fallback**: ONE shared host-native `omlx serve --model-dir <dir> --port 8100` process, NOT a container, reached by the LiteLLM container through the `host.docker.internal` gateway; unlike the vLLM design this replaced, omlx scans its own model directory and serves every model it finds — downloading/adding/removing/tuning a model happens entirely through omlx's OWN admin panel, reached with `ai services console omlx`, never through this CLI), and/or **colibri** ([JustVugg/colibri](https://github.com/JustVugg/colibri), a SECOND, OPTIONAL/best-effort local runtime alongside omlx — `internal/colibri` + `internal/setup/colibri_host.go` — a Python launcher (`coli`) wrapping a compiled engine binary, run as ONE always-on host process serving ONE configured model (confirmed from source: its `/v1/models` route lists only the single configured `model_id`), started/adopted/health-polled by `colibri.Manager.EnsureServed` (`coli start --background --no-browser --json`, polling `GET /health`), exposing OpenAI- AND Anthropic-compatible HTTP endpoints plus its own local web dashboard. UNLIKE omlx, colibri is NEVER required: `startColibriServerHost` swallows every failure mode (not installed, not configured via `coli setup`, start failure) and never returns an error, so a colibri-less host behaves exactly as before) — or a cloud provider; Headroom, Presidio, and LiteLLM are shared host containers (omlx/colibri are host-side, never containers). (Headroom is NO LONGER a Caddy proxy in front of LiteLLM — Caddy forwards the model path DIRECTLY to LiteLLM, and LiteLLM's `headroom` guardrail POSTs the request messages to `http://aip-headroom:8787/v1/compress` to compress them before dispatch.) **The sandboxed agent CLI is now a REAL HOST PROCESS** — opencode/claude-code/codex/gemini/omp/hermes run directly on the host, installed either via their own official installer (`ai setup` best-effort installs claude-code/codex/opencode, `internal/setup/agentcli_host.go`) or by the user; `Manager.Agent` fails fast with an actionable message if the selected CLI's binary isn't on PATH. There is no baked workspace image, so there is also no in-workspace Headroom/zsh/oh-my-bash install anymore and no per-shell managed `.bashrc`/`.zshrc` block — `workspace.Shell` (config.yaml `workspace.shell`, `bash` default or `zsh`) just picks which binary `ai shell` launches inside the sandbox, nothing more. **Caveman**, the per-project output-compression toolkit, is installed the same way it always was — by Caveman's OWN installer (`https://raw.githubusercontent.com/JuliusBrussee/caveman`) — but now runs directly on the HOST at every `ai agent`/`ai shell` launch (`workspace.registerCaveman`, once-guarded by a project-local marker, best-effort, DETACHED since it clones a repo and runs a node installer), giving each caveman-detectable CLI (claude-code/opencode/gemini/codex — mapped to `--only <agent>`; omp has no token and gemini is skipped for the install itself because its extension-install step blocks forever on a TTY-less exec) its native skills+agents+commands, then mirroring opencode's global caveman dirs into the shared `.ai-platform` pool so omp/gemini pick them up too. Credentials are **keys-in-LiteLLM plus OS-keychain injection**: real provider API keys are added via `ai keys` and live ENCRYPTED in the LiteLLM gateway's Postgres credential store (encrypted at rest by `LITELLM_SALT_KEY`), never on platform disk or in the project directory — the agent holds only a scoped LiteLLM **virtual key**, minted fresh per launch (revoking any prior one for the project) and stored ONLY in the host OS keystore (macOS Keychain via `security`, Linux via `secret-tool` — `internal/nono/keychain.go`), handed to the sandboxed process exclusively via nono's `--env-credential-map <keychain-ref> <ENV_VAR>` at launch (`nono.RunOptions.EnvCredentialMap`) — the real secret never appears in a config file, in argv, or on disk anywhere; only its keychain reference name does. The served model set is catalog-driven (models.dev) and DB-backed: adding/removing a provider key syncs that provider's models in/out of LiteLLM's DB, so there is no `model_list`/wildcards/named aliases in the rendered config. **Workspace egress is now a project's nono profile `network` block**, edited via `ai network` and compiled fresh into the profile at every launch (`internal/egress` mutates `config.yaml`'s `network.egress`/`allow_domain`/`deny_domain`; `internal/workspace.ensureProfile` renders it into the nono profile's `Network` section): the only two modes are `public` (DEFAULT — nono's own unrestricted-outbound default) and `deny` (nono's `--block-net`, carved open only by explicit `allow_domain`/`*.suffix` entries) — there is no `unrestricted` mode and no published-ports/host-services concept anymore (nono sandboxes a single host process directly; there is no guest network to publish a port from). `ensureProfile` always force-appends the resolved gateway host to `allow_domain` regardless of the project's own `deny` policy — a `deny` posture is meant to fence off the INTERNET, not the agent's own LiteLLM gateway, which every agent needs for every request; without this an `ai network egress deny` would silently break the very agent it's supposed to sandbox. Separately, every DNS name resolved host-wide (across all workspaces) is still logged for audit by the `aip-dns` CoreDNS resolver (`ai network log`, unchanged service-tier plumbing) — but **whether nono-sandboxed host processes' DNS resolution is actually routed through `aip-dns` post-migration is unclear**: the microVM-era `--dns-nameserver` wiring that forced this is gone (there is no guest network to force), and no equivalent host-process DNS-redirection was found in `internal/nono`/`internal/workspace`, so `ai network log` may simply show nothing for sandboxed sessions now — verify before relying on it as an enforcement signal (enforcement itself is the nono profile's own network policy, shown by `ai network show`). The **ten opt-in AI tools** (caveman, graphify, code-review-graph, codebase-memory-mcp, openviking, tokensave, agentmemory, ponytail, agent-skills, serena — chosen from one multi-select at `ai create`, toggled after the fact with `ai tools enable|disable <tool>`) are installed directly onto the HOST at every `ai agent`/`ai shell` launch rather than baked into an image; see the Architecture section below for the full per-tool breakdown and the important HOME-scoped-state scope change this migration introduced. Go 1.26, a single self-contained **pure Go** binary — **no cgo** (the old Microsandbox Go SDK cgo binding is gone entirely): the CLI wraps the external `nono` CLI via plain `os/exec`, so `CGO_ENABLED=0` builds and cross-compiles cleanly. Module `github.com/jt-helsinki/stack-genie`.

**`spec/` is the source of truth, not documentation.** The six numbered specs define the end-state architecture (`01`), delivery slices (`02`), on-disk/repo layout (`03`), the exact CLI surface + JSON envelope + exit codes (`04`), acceptance tests (`05`), and the milestone build plan (`06`). Code comments cite spec sections (e.g. `§17`, `CLI §3.1`, `repo-layout §12.5`) — when changing behavior, read the cited section first and keep code and spec in sync. The build proceeds in milestones **M0–M8** (see `spec/06`), with later work organized as slices **S1–S6** (`spec/02`). The full surface is implemented host-side and unit-tested with fakes; the nono-based workspace model (session create/attach/stop, OS-keychain credential injection, per-session nono-profile network enforcement, host-native agent-CLI installers) has **not yet had its own live-hardware verification pass** post-migration — the previous verification record (under the retired Microsandbox-microVM design) no longer describes the live code. The Docker-based service tier (Caddy, LiteLLM, the guardrails, Valkey, the DNS audit resolver, omlx) is unaffected by the migration and remains verified end-to-end on a provisioned host. The seams still needing a live check are grep-able (`hardware bring-up`) and tracked in detail in `docs/HARDWARE-BRINGUP.md` (which also enumerates, as a historical record, everything the migration removed outright: workspace OCI image build, in-VM container runtime, in-VM apps, `ai mounts`, `ai resize`, OS/stack selection at create, and tmux-based in-VM session multiplexing). Before changing a slice, read its milestone in `spec/06` and its `[Sx]`-tagged tests in `spec/05`.

CI (`.github/workflows/ci.yml`) is split: a hosted `ubuntu-latest` runner does build/vet/lint/unit-tests, and a SECOND hosted `ubuntu-latest` job (`acceptance-s1`, `workflow_dispatch`-gated until confirmed green) installs `nono` via its curl installer and runs the `[S1]` acceptance suite — unlike the Microsandbox-microVM design this replaced (Apple Hypervisor, Apple-Silicon-only, requiring a self-hosted macOS runner), nono's Landlock/Seatbelt sandboxing has no virtualization requirement, so the full stack now runs on a plain hosted runner. Before committing, run **`make check`** (= `fmt-check vet vet-tagged lint test build`) — it must all pass. `errcheck` + the rest of golangci-lint are strict, so explicitly discard intentional writes (`_, _ = fmt.Fprintln(...)`) and keep `make lint` clean.

## Architecture (the parts that span files)

**Output envelope is the universal contract.** Every command returns the `internal/output` envelope (`{ok, command, data, error, warnings}`, CLI §19). `error.code` **equals** the process exit code (§18: 0 ok, 2 invalid input, 3 missing dependency, 4 runtime failure, 5 permission). Pattern: `Execute()` (in `internal/cli/root.go`) owns an `exitCode` int and an `Emitter`; each cobra command's `RunE` does its work and sets `*exit = emitter.Success(...)` or `emitter.Failure(...)`, returning `nil`. Errors that must carry a specific exit code are `*output.Error` (build with `output.Errorf(code, ...)`); the emitter unwraps them. cobra/arg errors are mapped to exit 2 in `Execute`. Output is **human-readable by default**; the JSON envelope is emitted only with `--json` (commands provide a typed result + a Human renderer — see `ai logs`).

**Workspace runtime: `internal/workspace` wraps `internal/nono`, there is no Sandbox-interface backend split anymore.** The old `internal/sandbox` detection package and the two `Sandbox` implementations (`workspace_sdk.go`/`workspace_real.go`, the Microsandbox Go SDK vs. the `msb`-CLI shell-out) are gone entirely, along with `internal/envimage` (OCI image build) and `internal/overlay` (the VM-disk persistence overlay — the project directory on host IS the persistent state now, so there is nothing to overlay). `internal/workspace/workspace.go`'s `Manager` is the whole surface: `Agent(project, cli)` mints/stores the scoped key, writes the CLI's config, runs `registerAITools`, generates the nono profile (`ensureProfile`, `profile.go`), and launches a detached nono session (`Runner.RunDetached`); `Shell(project)` does the same minus the per-CLI config, launching `projectConfig.Workspace.Shell` (default `bash`) via `Runner.Shell`; `Attach(sessionID)`/`ListSessions(project)`/`Stop(sessionID, force)`/`StopAll(project)` wrap the matching `nono.Runner` calls (`ListSessions` filters nono's host-wide `ps` output down to sessions whose `Workdir` equals the project root, since nono's own session list is global across every project on the machine); `DeleteCredentials(project)` revokes the LiteLLM key and removes the keychain entry (called from `ai delete`). `agentValidCLIs` is the exact installable set — `opencode`/`omp`/`claude-code`/`codex`/`gemini`/`hermes` — each mapping to its PATH binary name and the env-var name its scoped key is injected under (`AIP_GATEWAY_KEY` shared by opencode/omp/codex/hermes; claude-code and gemini get their own provider-specific var names via `agentcfg.ClaudeAuthEnvVar`/`GeminiKeyEnvVar`). `Manager.Runner`/`Keys`/`Served`/`Credentials` are the four injectable seams (mirroring the project's established fake-in-tests pattern) — `nono.Runner` (real vs. `FakeRunner`), `KeyMinter` (LiteLLM virtual-key mint/revoke), `ServedModels` (the gateway's live model list for the per-CLI model picker), `CredentialStore` (OS keychain store/delete) — `RealManager(now)` wires the production implementations (`nono.RealRunner{}`, a real `litellm.KeyManager`, `realCredentialStore{}` over `internal/nono.StoreCredential`/`DeleteCredential`).

**`internal/nono` is a thin, faithful wrapper over the external `nono` CLI (https://nono.sh) — never invented.** `nono.go` defines `Detect` (PATH lookup only, no install), the `Profile` JSON schema this platform actually populates (`Meta`, `Extends` — a profile ALWAYS implicitly extends `"default"` even when empty — `FilesystemCapabilities{Allow,Read,Write}`, `NetworkCapabilities{Block,AllowDomain,DenyDomain,NetworkProfile,CustomCredentials}`, `EnvCredentials`, `Environment.SetVars` for plain non-secret vars like a gateway base URL), `WriteProfile` (atomic temp-file+rename, JSON not YAML since nono requires JSON), and `PullPack` (best-effort `nono pull <pack>` with `NONO_AUTO_MIGRATE=1` for non-interactive automation, used to extend a profile from an official registry pack). `session.go` defines the `Session` struct (captured live against nono v0.79.0 field names — `SessionID`, `Name`, `Status` "running"/"exited", `Attachment` "attached"/"detached", `Workdir`, etc.) and the `Runner` interface — `RunDetached` (`nono run --detached`, parsing nono's `"Started detached session <id>."` confirmation off STDERR, not stdout, which is reserved for the wrapped command's own output), `Attach`/`Shell` (real PTY passthrough of the current process's stdin/stdout/stderr), `ListSessions`/`Inspect` (`nono ps --json`/`nono inspect --json`), `Stop` (`nono stop [--force]`) — with `RealRunner` (shells out) and `FakeRunner` (records calls, in-memory) as the two implementations. `keychain.go` implements `StoreCredential`/`DeleteCredential` against the service name `"nono"` (matching nono's own documented `--env-credential-map`/`env_credentials` convention from its OpenCode client-integration guide): macOS via `security add-generic-password` — note `security -w` with the value OMITTED from argv prompts interactively via a PTY the code drives (`storeCredentialDarwin`; a bare stdin pipe does NOT work, `security` reads via `getpass(3)` against the controlling terminal) so the secret never appears in `ps`/argv listings — and Linux via `secret-tool store`/`clear` (Secret Service). `profile.go`'s `ensureProfile(root, cli, projectConfig, gatewayURL)` is called before every launch (`Manager.Agent`/`Shell`) and ALWAYS rewrites the profile (cheap — a few lines of JSON) so a `config.yaml` network change takes effect on the very next launch with no restart concept; `nonoPackForCLI` extends a fresh profile from an official registry pack for `opencode`/`claude-code`/`codex` (`nolabs-ai/<cli>`, best-effort/20s-bounded pull — an offline/slow registry never blocks a launch, the profile just falls back to extending nono's built-in `"default"`); a bare `Shell` launch (empty `cli`) has no pack and uses `"default"` directly. For `gemini` specifically (which has no config-file base-URL setting), the gateway root is written as a plain, non-secret `Environment.SetVars` entry (`GOOGLE_GEMINI_BASE_URL`) rather than a config file. **The gateway-reachability bug fix (this session):** `ensureProfile` computes `gatewayHostFromURL(gatewayURL)` (the bare hostname, e.g. `127.0.0.1`) and force-appends it to `AllowDomain` whenever it is non-empty and not already present — this applies UNCONDITIONALLY, even when the project's own `Egress` is `"deny"`, because a `deny` policy is meant to fence off the open internet, not the agent's own LiteLLM gateway that every request needs; without this fix, `ai network egress deny` would silently break the very agent it's supposed to just sandbox.

**Credential flow end to end.** `Manager.ensureScopedKey(project)` best-effort revokes any prior key by alias (`Keys.DeleteKeyByAlias(project)`), mints a fresh one (`Keys.GenerateKey(litellm.KeyScope{Alias: project})`), and stores it ONLY in the OS keystore under `credentialName(project)` = `"aip-gateway-" + project` (stable per project, so re-minting overwrites in place rather than accumulating keychain entries) — the key value itself is handed back to the caller just long enough to pick the api-key-vs-oauth SHAPE of the config file being written (`writeAgentConfig`'s `key != ""` check), never to write the value anywhere. At launch, `nono.RunOptions.EnvCredentialMap` maps that keychain reference name to the destination env var (`spec.credentialEnvVar`), which nono resolves from the OS keystore and injects into the sandboxed process's environment via `--env-credential-map <ref> <ENV_VAR>` — the secret crosses argv/disk/config only as a NAME, never a value. An oauth-mode CLI (claude-code/codex/gemini set to `"oauth"` in `config.Agent.AuthMode(cli)`, `config.IsOAuthEligible`) skips all of this entirely — no key minted, no `EnvCredentialMap`, and `writeAgentConfig` writes the CLI's own native-login config shape instead (empty `key` argument).

**Agent CLI configs are written at each CLI's own default per-project (or per-user) location, now on the HOST filesystem directly — `internal/workspace/agentconfig.go` is the per-CLI dispatch.** `writeAgentConfig(root, cli, projectConfig, gatewayURL, key)` dispatches to: `writeOpenCodeConfig` → `<project>/.opencode/opencode.json` (deep-merged via `agentcfg.MergeOpenCodeConfig` so user edits survive, fed the live served-model picker via `Manager.pickerModels()` and the project's Headroom `keep_turns`/`output_buffer_tokens` knobs); `writeClaudeConfig` → `<project>/.claude/settings.json` (`MergeClaudeSettings` for api-key, `MergeClaudeSettingsOAuth` to blank the gateway env block for oauth); `writeCodexConfig` → `<project>/.codex/config.toml` PLUS an idempotent APPEND-ONLY trust entry into the GLOBAL `~/.codex/config.toml` (`appendCodexTrust` — unlike the retired per-project-isolated microVM, `~/.codex/config.toml` is now SHARED across every project on this host, so this only ever appends a missing `[projects."<root>"]` block, never rewrites the file wholesale, to avoid destroying another project's trust entry); `writeOmpConfig` → the GLOBAL `~/.omp/agent/models.yml` PLUS `<project>/.omp/config.yml`; `writeHermesConfig` → the GLOBAL `~/.hermes/config.yaml` (pointed at the project's shared skills pool); `gemini` gets no config file at all — purely env-only via the nono profile's `Environment.SetVars` (see above). `headroomParams(strategy)` mirrors `internal/contextopt.HeadroomParams`'s three presets (conservative 8/12000, aggressive 2/4000, default/balanced 5/8000) locally to avoid a dependency edge. **Headroom wrapping is now opportunistic, not platform-installed:** there is no workspace image to bake `headroom-ai[proxy]` into anymore, so `Manager.Agent` just checks `exec.LookPath("headroom")` at launch time and, if found, wraps a wrappable CLI's launch command as `headroom wrap <token>` (`agentcfg.HeadroomWrapName` — claude-code/codex/opencode only; omp/gemini/hermes are not supported by Headroom's own `wrap` subcommand) — this check runs UNCONDITIONALLY for every launch of a wrappable CLI, not just oauth-mode ones (unlike the old in-VM design, which only aliased oauth agents since api-key agents already got compression gateway-side via LiteLLM's `headroom` guardrail); whether double-wrapping an api-key agent that also goes through the gateway's own Headroom guardrail is desirable is worth a second look if the user has `headroom` on PATH.

**AI tools are a HOST-WIDE, project-gated install system — `internal/workspace/tools.go` (922 lines, newly written this session) is the single file implementing all nine.** Its package doc comment states the key architectural consequence of the migration precisely: under Microsandbox, each tool's HOME-scoped state (a `gemini extensions install`, hermes's own venv, OpenViking's one `openviking-server` process) was safely isolated per-workspace-VM; nono sandboxes a single host process, not a virtualized `$HOME` or a separate OS per project, so that HOME-scoped state is now **SHARED MACHINE-WIDE** across every project that enables the tool — a deliberate, named scope change, not a bug. OpenViking is the sharpest example: it runs ONE persistent server on a FIXED port (`127.0.0.1:1933`), pgrep-guarded (`registerOpenViking`) so a second project enabling it just reuses the already-running instance rather than conflicting, and disabling it in ANY one project's `ai tools disable openviking` stops that shared server for every other project that still has it enabled too (an accepted consequence — the next launch of any project with it enabled simply restarts it). Project-SCOPED state (anything written into `<project>/.ai-platform` or the project directory itself) stays correctly per-project, since the project directory IS the real host directory now, not a bind-mounted VM copy. `Manager.registerAITools(root, projectConfig)` runs all ten register steps on EVERY `Manager.Agent`/`Shell` call — cheap after the first run because each is gated by its own project-local marker file (`<project>/.ai-platform/.<tool>-installed`) — in this order: `linkSharedResources` FIRST (so the shared `<project>/.ai-platform/{agents,skills,prompts,projects}` pool is symlinked into each installed CLI's real per-project dir before anything writes into it), then `registerGraphify`, `registerCaveman`, `registerCodeReviewGraph`, `registerCodebaseMemory`, `registerOpenViking`, `registerTokenSave`, `registerAgentMemory`, `registerPonytail`, `registerAgentSkills`, `registerSerena`. Each register function also has a matching `teardown*` that runs when the tool's `context.*_enabled` flag flips to false (`ai tools disable <tool>` or unchecking it doesn't exist at create — only the initial create wizard can set it on, `ai tools enable|disable` afterward) — teardown is config-only, best-effort, and for several tools explicitly documented as a GAP where the upstream tool ships no confirmed uninstall verb (code-review-graph, codebase-memory-mcp, agentmemory, ponytail's/agent-skills' gemini-extension removal are all "attempted best-effort, may go stale harmlessly"). A slow step (network clone/install/build: caveman, code-review-graph, openviking, tokensave, agentmemory, ponytail, agent-skills) runs via `runDetachedScript` (its own process group, released immediately, logged to `<project>/.ai-platform/run/<tool>-install.log`); a fast config-only step (graphify's git-init + `graphify install`, codebase-memory-mcp's auto-detecting `install`) runs via `runBlockingScript` (bounded `context.WithTimeout`). `registerGraphify` ALSO always `git init`s the project when it isn't already a valid git working tree (detected with `git rev-parse --is-inside-work-tree`, not a bare `.git`-dir test, since a dangling `.git` gitlink file needs removing first) — this runs regardless of whether Graphify itself is enabled, so every workspace stays git-backed. `graphify`/`code-review-graph`/`codebase-memory-mcp` additionally register themselves as MCP servers with the agent CLIs that support it (`agentcfg.EnabledMCPServers`/`AppendCodexMCP`/`InjectHermesMCP`/`OmpMcpConfig` exist in `internal/agentcfg/agentcfg.go` for this, though as of this doc pass `EnabledMCPServers` is not actually called from `internal/workspace` — codex/hermes/omp's MCP wiring for these three tools appears to still be a TODO, not yet invoked from the register functions above; verify before relying on it). **Known dead code:** `config.AgentConfig.GraphifyModel` (`agent.graphify_model` in `config.yaml`, seeded by `ai create`'s Graphify-model picker) is captured and persisted but never read by any config writer — `agentcfg.OmlxModelHandle` (which would turn it into `omlx/<name>` for a provider config) exists but is called from nowhere in `internal/workspace`; this is a pre-existing "seed-then-remember default model" feature from the old microVM design that was never ported to the host-process model, not a new regression.

**Egress policy is a project-config-to-nono-profile pipeline, not a VM net-rule renderer.** `internal/egress` (`egress.go`) edits `config.yaml`'s `network.egress` (`"deny"`/`"public"`, `config.EgressModes`) and `allow_domain`/`deny_domain` lists — `Get`/`SetMode`/`Allow`/`Deny`/`Clear`, each validating hosts permissively (`ValidateHost` rejects empty/whitespace/URL-scheme/`/`-containing hosts and requires a `*.suffix` wildcard to have at least two labels) and persisting via `config.WriteProject`. `ai network show|egress|allow|disallow` (`internal/cli/network.go`) front this directly; `ai network log` is a SEPARATE, unrelated read of the `aip-dns` service-tier container's CoreDNS query log (`internal/cli/networklog.go`, parsing its `log`-plugin lines) — see the "What this is" section above for why its relevance to nono-sandboxed traffic is currently unclear. There is nothing to "apply" beyond the config write: `internal/workspace/profile.go`'s `ensureProfile` reads `config.yaml`'s `Network` block fresh on every launch and compiles it straight into the nono profile's `NetworkCapabilities{Block, AllowDomain, DenyDomain}` — `Block` is `true` only when `ResolvedEgress() == "deny"` (empty defaults to `"public"`, nono's own unrestricted-outbound default). No published ports, no host-service allow-list, no `unrestricted` mode — all retired along with the VM boundary that made them meaningful.

**Newer/unchanged packages worth knowing, per-agent auth mode, and the shared resource pool.** `internal/omlx` (the host-side manager for the omlx local-inference server — the SOLE local runtime, macOS/Apple-Silicon only; entirely unaffected by this migration) resolves the LATEST `github.com/jundot/omlx` GitHub release's newest-Python-version prebuilt wheel and pip-installs it into the platform venv (`~/.ai-platform/venv`, `internal/pyenv`), pinning the venv's Python version to match via `pyenv.EnsureVersion`; `omlx.Manager.EnsureServed` starts/adopts/waits-on the ONE shared `omlx serve --model-dir <dir> --port 8100` process (weights at `~/.ai-platform/volumes/models/omlx`, OS-level-flock-serialized across `ai` invocations since `ai` is daemonless); `omlx.ListModels` reads the running server's live `GET /v1/models` — the single source of truth for served local models, since model management (download/add/remove/tune) lives ENTIRELY in omlx's own admin panel (`ai services console omlx`), never in this CLI. `internal/contextopt` (Headroom strategy + Caveman level, per-project, surfaced by `ai context`) maps the strategy to Headroom's `keep_turns`/`output_buffer_tokens` body knobs — now baked into the agent CLI's request `extra_body` at EVERY `ai agent` launch (`workspace/agentconfig.go`'s `headroomParams`), not at a one-time "workspace start" as under the old design. `internal/console` is the admin-dashboard URL registry for `ai services console`; `internal/litellm` is the LiteLLM admin/virtual-key client (`KeyManager`). `internal/uninstall` tears down the platform; its workspace-stop step (`stopWorkspaces`) is a **known, currently-unfixed gap**: it still shells out to the retired `msb list`/`msb stop -f` (`internal/uninstall/uninstall.go`, not yet ported to `nono.Runner`/`workspace.Manager.StopAll`) — since `msb` is no longer installed by anything, this now silently no-ops (`LookPath("msb")` fails, the function returns 0 stopped), so a plain `ai uninstall` does NOT actually stop any live nono sessions before removing service-tier images; worth fixing before relying on it. **Per-agent auth mode** (`config.AgentConfig.AuthModes`, `agent.auth_modes` in `config.yaml`, keyed by CLI): the three CLIs with a first-party subscription login — claude-code, codex, gemini (`config.OAuthCapableCLIs()`) — each record `api-key` (DEFAULT — route through the gateway with the scoped virtual key, keeping the tool firewall/secret masking in effect) or `oauth` (the CLI's own subscription login, direct to the provider, bypassing the gateway and its guardrails); opencode/omp/hermes have no subscription and are ALWAYS gateway/api-key. `config.ForcedOAuthCLIs()` is a generic mechanism for a CLI that is OAuth-only / gateway-incapable — currently an EMPTY set (GitHub Copilot CLI, its only past member, was removed from the platform entirely) — retained for a future CLI with that constraint. An oauth-mode CLI gets no scoped key minted/injected at all (see the credential-flow paragraph above) and `project.Scaffold` pre-allow-lists its own provider's egress domains (`agentcfg.OAuthProviderDomains`) so it can still reach its provider even under a `deny` policy; `create.Execute` emits a warning for each oauth agent selected (its traffic bypasses the firewall/masking/content-egress-audit entirely). **Shared resource pool + symlinks** (`linkSharedResources`, `internal/workspace/tools.go`): `<project>/.ai-platform/{agents,skills,prompts,projects}` is symlinked (relative, idempotent, never clobbering a real user file) into each installed CLI's real per-project dir — skills → `.opencode/skills`/`.claude/skills`/`.omp/skills`/`.hermes/skills`; agents → `.opencode/agents`/`.claude/agents`/`.omp/agents`; prompts → `.opencode/commands`/`.claude/commands`/`.gemini/commands`/`.omp/commands` (a CLI absent from a kind's map is skipped — codex/gemini have no skills/agents concept). This runs FIRST in `registerAITools`, before any tool writes into the pool, so Caveman/Graphify/Ponytail/agent-skills' shared-pool writes reach every skill-capable CLI through it.

**Dual runtime model.** nono sandboxes agent/shell processes directly on the host; Docker/Podman run the service tier on the shared `aip-net` network, reconciled in order network → DNS → Presidio → Valkey(+RedisInsight) → Headroom → LiteLLM(+DB) → Open WebUI → Caddy proxy (LAST) — Headroom precedes LiteLLM now because LiteLLM's `headroom` compression guardrail calls it (omlx is host-side, not part of this container reconcile). **Odysseus has been removed from the platform entirely** (no host container, no docker-socket mount); `internal/apps` and the whole in-VM-app concept are gone along with the VM. **Open WebUI is back as a CORE host service** (`aip-open-webui`, `internal/setup/setup_real.go`'s `ensureOpenWebUI`) — unlike its old per-workspace in-VM-app incarnation, there is no setup picker, no enable/disable, no optional-services gate: it is always installed, reconciled at every `ai setup`, and started/stopped/restarted with the rest of the tier via `ai services <action> open-webui` (or `all`). It is INTERNAL-ONLY, fronted by Caddy at `chat.<domain>` like every other UI vhost, and its own model calls route through the SAME gateway path every workspace agent uses (`http://aip-proxy/v1`) so LiteLLM's guardrails still apply; it authenticates that traffic with a DEDICATED SCOPED LiteLLM virtual key (`ensureOpenWebUIKey`, minted under the stable alias `aip-open-webui`, revoked+re-minted on each launch) — NEVER the LITELLM_MASTER_KEY, so a compromised Open WebUI instance can only make inference calls, not mint/revoke keys or read provider credentials. There are currently NO optional host services — the optional MECHANISM is retained (empty set) for a future genuinely-optional service. **`aip-proxy` (Caddy) is the SOLE host entry point to the service tier: every other service container is INTERNAL-ONLY on `aip-net` (reached by name) — only Caddy publishes ports to the host** (besides the loopback-only `aip-dns` :15353; `aip-litellm-db` is INTERNAL-ONLY, no host port). The services: `aip-dns` (CoreDNS egress-audit resolver, bound to host loopback `127.0.0.1:15353/udp`; it forwards upstream to the CONTAINER'S OWN `/etc/resolv.conf` — Docker's embedded DNS, which inherits the host resolver — NOT hardcoded public resolvers like 1.1.1.1/8.8.8.8, so it still resolves on restricted/corporate networks that block direct external DNS; **whether a nono-sandboxed host process's own DNS resolution is routed through it post-migration is unclear** — see the egress paragraph above, since there is no guest network left to force a `--dns-nameserver`-style redirection through), **omlx** (the SOLE local-inference backend — host-side, no `aip-*` container, **macOS/Apple-Silicon only** — the ONE remaining Apple-Silicon-only constraint on the platform; nono itself has no such requirement): ONE SHARED host process — `omlx serve --model-dir <dir> --port 8100` (`internal/omlx`, port fixed at `services.OmlxPort`) — that scans its own model directory (`~/.ai-platform/volumes/models/omlx`, `omlx.StoreDir`) and serves EVERY model it finds, an OpenAI-compatible endpoint on that ONE host loopback port (probed by the platform at `http://127.0.0.1:8100/v1/models`; the LiteLLM container reaches it at `http://host.docker.internal:8100/v1` via `--add-host=host.docker.internal:host-gateway`). Model download/add/remove/tune all live entirely inside omlx's own admin panel at `http://127.0.0.1:8100/admin`, reached with `ai services console omlx`. The `aip-presidio-analyzer`/`aip-presidio-anonymizer` pair backs LiteLLM's opt-in secret-masking guardrail (started ONLY when `secret-masking` is selected at `ai setup`; reported "disabled" in `ai services` otherwise), `aip-valkey` (a SINGLE `valkey/valkey:9.1.0-alpine` instance backing LiteLLM's response cache, INTERNAL-ONLY on `aip-net` at `aip-valkey:6379`, NO persistence volume; LiteLLM points at it via `litellm_settings.cache: true` + `cache_params{type:redis}` PLUS `REDIS_HOST=aip-valkey`/`REDIS_PORT=6379` env vars) and its web GUI `aip-redisinsight` (RedisInsight, web port 5540, INTERNAL-ONLY, surfaced to the host as the Caddy UI vhost `valkey.<domain>`), `aip-litellm` (the gateway, INTERNAL-ONLY — reached by name at `aip-litellm:4000` by Caddy's model path + `/llm` route, and it in turn calls Headroom at `aip-headroom:8787/v1/compress`) plus a small `aip-litellm-db` Postgres (INTERNAL-ONLY, no host port, HOST BIND MOUNT data dir at `~/.ai-platform/volumes/litellm-db`), `aip-headroom` (the input-compression SERVICE LiteLLM calls as a `pre_call` guardrail — no longer a Caddy proxy in front of LiteLLM, INTERNAL-ONLY on :8787), and `aip-proxy` (the Caddy reverse proxy, the SOLE host ENTRY on :18787: `/v1` → `aip-litellm:4000` DIRECTLY, `/llm` → the LiteLLM admin surface, the UI vhosts `litellm.<domain>`/`valkey.<domain>`/`chat.<domain>` data-driven from `services.UIVhosts()`; reconciled LAST, after `open-webui` so its upstream already exists when Caddy resolves it at config-load). The `<domain>` is the resolved platform base domain (`runtime.yaml` `domain`, default `aip.local`); **standalone** `ai setup` writes an `/etc/hosts` managed block pointing the UI subdomains + the bare platform domain at `127.0.0.1`, **server** prints the DNS/TLS operator contract instead. The host CLI reaches LiteLLM through Caddy, never a container directly (`litellm.AdminBaseURL`/`GatewayBaseURL`); the sandboxed agent's `/v1` path is now a **plain loopback connection** (`127.0.0.1:18787/v1` → Caddy → LiteLLM) since the agent runs directly on the host — there is no guest-network DNS name to translate anymore. There is no native firewall service; provider credentials live in LiteLLM (keys-in-LiteLLM). Detection (`internal/runtime` + `internal/nono`) is parameterized by `GOOS/GOARCH` + a `Prober` so it tests on any host; missing deps → exit 3, a missing rootless container runtime → exit 4. **The old macOS-Apple-Silicon-only host gate is GONE along with Microsandbox** — nono has no virtualization-capability requirement at all; the platform now runs on any macOS or Linux host, Apple Silicon or not (the sole remaining Apple-Silicon constraint is the OPTIONAL omlx local-inference backend, not the workspace runtime itself). **Deployment roles** (chosen interactively by `ai setup`, or `--mode`, persisted as `role:` in `runtime.yaml`): **standalone** (default — full service tier + sandboxed sessions here; shared services bind **127.0.0.1**), **server** (only the service tier, bound **0.0.0.0** for remote clients, no local sessions — preflight needs only docker + rootless), **client** (only sandboxed sessions; routes to a remote `--server` address held in `ai_platform_host`, skips the local reconcile — preflight needs only the **`nono runtime`** check, since there is no virtualization capability left to probe). The role drives `blockingPrereqsForRole` and the `bindHost` threaded through `Services.Reconcile`/`ensure*` (Postgres + DNS stay loopback regardless); since the service containers are internal-only, `bindHost` governs only what **Caddy (`ensureProxy`)** publishes. Per-project workspace egress (modes `public`[default]/`deny`, allow/deny domain lists, stored in `config.yaml`) is declared via `ai network` and compiled into the project's nono profile at every agent/shell launch — see the dedicated egress paragraph above; there is no published-port, host-service-list, or msb-style net-rule host-group-token mechanism anymore. **Model gateway wiring** (`ai gateway show|set|clear`, `internal/cli/gateway.go`): the machine-wide `ai_platform_host` in `runtime.yaml` (set by `ai gateway set <host[:port]>` or `ai setup --mode client --server`) selects which gateway every sandboxed agent session on this host routes through. `internal/workspace` derives it at launch via `runtime.ResolveGateway(Info.HostAddress())` — bare host or `host:port`, default port 18787; empty → plain loopback `127.0.0.1:18787` (`runtime.DefaultGatewayHost`, standalone/local) — and uses the resolved `http://<host>:<port>/v1` for the agent provider configs' `base_url`; the resolved bare hostname is also what `ensureProfile` force-appends to the nono profile's `AllowDomain` so the gateway stays reachable under a `deny` egress policy. `ai gateway` exits 3 (no runtime.yaml — run `ai setup`), 2 (invalid address), 4 (persist/read failure). **Platform base domain** (`ai domain [name]`, `internal/cli/domain.go`) is unaffected by this migration: the machine-wide `domain` field in `runtime.yaml` is the base domain the Caddy UI subdomains hang off — `litellm.<domain>`, `valkey.<domain>`, `chat.<domain>` — defaulting to `aip.local` for local/standalone and overridden in server mode; `ai domain` with no arg SHOWS the resolved domain, with a name it VALIDATES + persists a lowercase DNS hostname, mirroring `ai gateway`'s load-modify-save + exit codes.

**Model catalogue is global, DB-backed, and catalog-driven — entirely unaffected by this migration.** Models are registered in LiteLLM's Postgres-backed model store (`general_settings.store_model_in_db: true`) — the rendered config has NO `model_list`, NO named aliases, NO per-provider wildcards, and NO default model (`litellm.DefaultRouting()` returns the ZERO `Routing`). The model set is driven by the **models.dev catalog** (`internal/catalog`, fetched as JSON and persisted as YAML to `~/.ai-platform/cache/catalog.yaml`): adding a provider API key via `ai keys` syncs that provider's catalog models INTO the DB, removing it syncs them OUT (`litellm.SyncModels`) — `SyncModels` NEVER deletes LOCAL (`omlx/*`/`colibri/*`) models, which are owned solely by the SEPARATE per-backend local syncs (`litellm.SyncOmlxModels`/`SyncColibriModels`, each driven by that backend's own live model list, never the catalog, and each scoped by `onlyPrefixedModels` so refreshing one backend can never touch the other's registrations). omlx ([jundot/omlx](https://github.com/jundot/omlx)) is the REQUIRED shared local-inference server and colibri ([JustVugg/colibri](https://github.com/JustVugg/colibri)) is the SECOND, OPTIONAL one (see the local-inference-backend paragraph above) — model download/add/remove/tune for BOTH lives entirely inside their own admin surfaces (omlx's web admin via `ai services console omlx`; colibri's own `coli setup`/web dashboard), never through this CLI's models command; this platform has NO `ai models pull/rm/configure/enable/disable` equivalent — `ai models` (`internal/cli/models.go`) is read-only gateway inspection plus one on-demand sync trigger: `status` (LiteLLM health/providers/routing + local omlx/colibri connectivity), `test [model]` (round-trips a served model through the gateway), and `refresh` (re-syncs BOTH LiteLLM's `omlx/*` AND `colibri/*` registrations against each backend's live model list ON DEMAND — `newModelsRefreshCmd` calls `syncOmlxModelsFn()` and `syncColibriModelsFn()` unconditionally; a colibri sync failure is captured as a string, not surfaced as a command failure, since colibri is optional — the same omlx sync `startOmlxServerHost` runs automatically at `ai setup`/`ai services start|restart omlx`). `litellm.SyncOmlxModels`/`SyncColibriModels` each run a FULL REBUILD (`syncLocalModels`) scoped to ONLY their own prefix: every registered one is DELETED then every model that backend currently reports is RE-ADDED fresh — registered as `omlx/<id>`/`colibri/<id>` (verbatim, no alias derivation) routed to `openai/<id>` against that backend's ONE shared `api_base`, authenticated with the backend's own opt-in API key (`omlx.APIKey`/colibri's `COLI_API_KEY`) or the placeholder `"EMPTY"` (LiteLLM's `openai/` provider hard-requires a non-empty key even against an unprotected server). The TUI's top-level view order is Services · Workspaces · Cloud Models · API Keys · Settings (no Local Models tab — omlx/colibri each manage their own models); Cloud Models lists the catalog ⨯ the gateway's live registered set, excluding local `omlx/*`/`colibri/*` models. `ai services start|stop|restart` manage the container set (presidio [only when secret-masking is enabled], valkey, redisinsight, headroom, litellm, open-webui, proxy, dns) plus **omlx** and **colibri** as host-native entries (Mode "host" — status via an HTTP health probe against `GET /v1/models`/`GET /health`; `enable`/`disable` on either is rejected, exit 2 — no such notion for a host-native runtime). `ai services compose` writes a DEBUG-ONLY `~/.ai-platform/docker-compose.yaml` mirroring the service-tier topology for local debugging with `docker compose`. The LiteLLM admin UI is secured with `UI_USERNAME`/`UI_PASSWORD`/`LITELLM_MASTER_KEY` passed by env passthrough (never in argv/config/disk); `ensureLiteLLM` always establishes a stable `LITELLM_MASTER_KEY`+`LITELLM_SALT_KEY` (minted on first launch, persisted to the 0600 `~/.ai-platform/.ai-platform.env` on request) because the master key mints workspace scoped virtual keys even in OPEN standalone mode, and a rotated salt key would silently orphan `store_model_in_db` credentials. **Password commands**: `ai litellm|omlx|colibri password` each prompt (hidden), store the secret and relaunch the service (`internal/cli/litellm.go`; omlx/colibri share `internal/cli/localbackend.go` — keychain `OMLX_API_KEY`/`COLI_API_KEY`, then `ControlService restart`; omlx also sets the `OMLX_API_KEY_CHOSEN` marker so `ai setup` stops prompting). **Role-based UI-auth policy** (`runtime.RequireUIAuth(role)`, true ONLY for `server`) — standalone/client run OPEN, server REQUIRES a password (`ai litellm password` sets one later on standalone).

**Multica (`multica`) is a CORE service with a container half and a host half**, wired per `SELF_HOSTING_ADVANCED.md`'s same-origin layout. The self-hosted server ([multica.ai](https://multica.ai)) is two INTERNAL-ONLY containers — `aip-multica` (web UI, the service's primary component) and `aip-multica-backend` — started by `ensureMultica` (`internal/setup/multica_server.go`) before the proxy and fronted at `multica.<domain>:18787`; the vhost routes `/ws` and `/ws/*` straight to the backend (`services.UIVhost.WebSocketUpstream`, rendered by `proxyCaddyfile` with `flush_interval -1`), everything else to the web UI (whose Next.js rewrites carry `/v1`, `/api`, `/auth`, `/uploads`). **There is no Multica database container**: its docs state it does NOT use pgvector (the bundled `pgvector/pgvector:pg17` image is a historical name) and needs only the `pgcrypto` and `pg_trgm` extensions, so it gets its own `multica` database + role in the existing LiteLLM Postgres via `ensureLiteLLMPostgresDatabase` (`shared_db.go`, shared with Langflow; it starts that Postgres if down and re-applies the extensions each time). Accepted tradeoffs: trust auth makes the role hygiene, not a boundary; `ai services stop|restart litellm` takes Multica's storage down; and the docs call for PostgreSQL 17 while `aip-litellm-db` is 18.4 (untested — `hardware bring-up`). Uploads are a bind mount at `~/.ai-platform/volumes/multica-uploads` → `/app/data/uploads` with `LOCAL_UPLOAD_DIR` set to that absolute path (the docs warn a relative default orphans uploads). Its `JWT_SECRET` is generated once into the OS keychain (`MULTICA_JWT_SECRET`) and passed by env passthrough; `COOKIE_DOMAIN`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_WS_URL` are explicitly empty (same-origin). The host half (`internal/setup/multica_host.go`, `internal/multica`) is best-effort and never fails `ai setup`: it installs the `multica` CLI via `internal/releasepkg` (fail-closed SHA-256 check against the release's `checksums.txt` — colibri still carries an older copy of that logic) and runs `multica config set server_url|app_url`. Following `SELF_HOSTING_AI.md`, an interactive `ai setup` then OFFERS to run `multica setup self-host --server-url <url> --app-url <url>` (`setup.MulticaSignIn`, `cli.setupMulticaSignIn`): browser sign-in, workspace discovery and daemon start. It runs after the progress UI (it owns the terminal) and only when the CLI is installed and signed out. **The daemon discovers agent CLIs by name on PATH and would otherwise run them bare on the host, so it — including the one `multica setup self-host` starts — runs with `multica.DaemonEnv`: a PATH whose first entry is `~/.ai-platform/bin/multica-shims` and platform secrets stripped**; the shims are written and the shared key minted BEFORE that command, so there is no unsandboxed window. Each shim (claude/codex/opencode/omp/hermes — Multica documents no gemini runtime) execs the hidden `ai multica-exec <cli> -- args…`, which runs the REAL binary (found with the shim dir stripped from PATH) under `nono run` (new foreground `nono.Runner.Run`) wired to the LiteLLM gateway. `--version` probes bypass the sandbox. Unlike `Manager.Agent` there is no project: the task cwd plays the root, ONE shared scoped key (`aip-gateway-multica`, minted once before the daemon starts by `EnsureMulticaKey` — a per-task mint would revoke every running task's key) is injected via `EnvCredentialMap`, and the profile (`~/.ai-platform/multica/nono-profile-<cli>.json`, never inside a task worktree) grants the Multica workspaces root + temp base on top of the CLI's pack, with default-open egress plus the gateway host. **This is a documented security-model exception, not full parity**: filesystem isolation is wider than a project's and egress is not per-project. `multica-exec` never uses the output envelope (stdout belongs to the agent) and propagates the agent's exit code. All of the host half is `hardware bring-up` (see `docs/HARDWARE-BRINGUP.md`).

**Langflow (`langflow`) is a CORE single-container service** (`internal/setup/langflow.go`): `langflowai/langflow` with its config dir on the named volume `aip-langflow-data` (`/app/langflow`), INTERNAL-ONLY, fronted at `langflow.<domain>:18787`. Its flows live in its OWN `langflow` database + role inside the existing LiteLLM Postgres (`aip-litellm-db`, created idempotently by `ensureLangflowDatabase`, which also starts that Postgres if it is down) — no SQLite and no DB container of its own. Accepted tradeoffs: that Postgres uses trust auth, so the separate role is hygiene not a boundary (a compromised Langflow could reach the LiteLLM database), and `ai services stop|restart litellm` stops that DB and takes Langflow's storage down with it. Like every registry service it gets `ai services start|stop|restart`, status, `ai logs --service langflow`, and `ai services console langflow` with no extra wiring. Auth follows `runtime.RequireUIAuth`: standalone/client run open (`LANGFLOW_AUTO_LOGIN=true`); server sets `LANGFLOW_AUTO_LOGIN=false` + `LANGFLOW_SUPERUSER=admin` with a password generated once into the OS keychain (`LANGFLOW_SUPERUSER_PASSWORD`), SHOWN ONCE in the setup output and passed by env passthrough (unset right after launch; also on `multica.DaemonEnv`'s strip list). Model access is NOT pre-wired — Langflow has no env hook for a base URL, so point its OpenAI provider at `http://aip-proxy/v1` with a LiteLLM key. `hardware bring-up`: first boot and the login through the vhost.

**Serena (`serena`) is the tenth AI tool** (`registerSerena`, `internal/workspace/tools.go`): PyPI `serena-agent` installed into the PROJECT Python environment `<project>/.venv-msb` — the same venv Graphify's MCP server expects. Nothing else creates that venv since the microVM went away (Graphify's step just exits when it is missing), so `registerSerena` runs `uv venv` itself when absent and needs `uv` on PATH. It registers with claude-code (`claude mcp add --scope local`, private to the machine — never the checked-in `.mcp.json`) and gemini (`--scope project`); codex/hermes/omp get it through `agentcfg.EnabledMCPServers`; opencode gets neither (same gap as agentmemory). The MCP server runs `serena start-mcp-server --project-from-cwd --open-web-dashboard False` with context `claude-code` or `ide-assistant`. Disabling removes the registrations and the marker but leaves the package in the venv. Install and registration are `hardware bring-up` (not yet run against a real `uv`/`claude`).

**The TUI (`ai ui`) lost a whole layer of complexity along with the VM it used to manage.** The top-level view order is unchanged — Services · Workspaces · Cloud Models · API Keys · Settings (`internal/tui/tui.go`) — and the Services tab's two-level drill-down (list → `views.ServiceDetail` with its own Service/Logs sub-tabs, live container stats via `setup.ServiceStats`) is entirely service-tier plumbing, so it is unaffected. The Workspaces hub, though, is much simpler now: **the per-workspace sub-tabs are exactly Workspace · Network · Context · Shell** — Logs, Metrics, Mounts, and Apps are GONE (there is no persistent microVM to stream logs/metrics from, no VM-guest mounts, and no in-VM apps anymore). `views.Project` (the "Workspace" sub-tab) shows the workspace summary plus a **Configuration** block (declared `config.yaml` fields — `os` [now just records the HOST's `runtime.GOOS` at create time, e.g. `darwin`/`linux` — a workspace OS is no longer selectable, there's no guest OS to pick], `shell`, `egress`, and allow/deny domains — via an injected `ConfigFetcher`) and a workspace-independent **Gateway Endpoints** block (the host Caddy entry to LiteLLM, resolved from `runtime.yaml`); its start/restart actions now SUSPEND the TUI directly into the user's real terminal via `tea.ExecProcess` (`WorkspaceActionRequestedMsg`, the same mechanism `ai shell`/`ai agent`/`ai attach` use) since launching a session is just exec-ing a CLI, not booting a VM that needs a progress spinner; stop runs in-process (`Manager.StopAll`, no sandbox to suspend into) since there's nothing to wait on; delete runs in the confirm overlay. **The "Shell" sub-tab (`views.Sessions`) is the session manager** over the project's live nono sessions (`SessionLister`/`SessionKiller` injected over `workspace.Manager.ListSessions`/`Stop`): it lists sessions and, on the selected row, attaches (`enter`/`a`, suspending into the real terminal via `tea.ExecProcess` running `ai attach`), creates a new one (`n`), or kills one (`d`/`k`) — auto-refreshing every 3s while the tab is visible so sessions appearing/disappearing show up without a manual refresh. The embedded **terminal pane** (`views.Terminal`, vt10x over a `creack/pty` PTY, `internal/tui/views/terminal.go`) still exists for the few remaining **non-interactive** overlays (service log follow, `ai services update`, keys/models flows) — it was never VM-specific to begin with. `internal/tui/views/logview.go` (the generic scrollable log component) still backs the Services-detail container log; it is no longer used for a workspace log, since there is no persistent workspace process to tail.

**State is split global vs project-local, written atomically.** Global lives under `~/.ai-platform/` (config, `runtime.yaml`, `versions.yaml`, `projects.yaml` index); per-project state lives in `<project>/.ai-platform/` (tracked `config.yaml`/`project.yaml`/`.gitignore` + the `{agents,skills,prompts,projects}` shared resource pool [Caveman and the other AI tools are NOT scaffolded here — they install into the pool at the first `ai agent`/`ai shell` launch], gitignored `run/` for install-script logs); the per-CLI provider configs are written KEYLESS at each CLI's own default location (`<project>/.opencode/`, `.claude/`, `.codex/`, or a GLOBAL `~/.omp/`/`~/.hermes/` dir) at every launch, not scaffolded at create. There is no Dockerfile and no project-level OCI image anymore — `internal/project`'s own package doc makes this explicit. All paths derive from `os.UserHomeDir()` via `internal/paths`, so **tests redirect with `t.Setenv("HOME", t.TempDir())`**. **All host-persisted SYSTEM data volumes live under `~/.ai-platform/volumes/<name>` (`paths.VolumesDir`)** — unaffected by this migration: `volumes/litellm-db` (the LiteLLM Postgres data dir, HOST BIND MOUNT) and `volumes/models` (the omlx weights store is the `volumes/models/omlx` subdir, entirely managed by omlx's own admin panel) — removed by `ai uninstall --purge`. **Re-fetchable caches live separately under `~/.ai-platform/cache/<name>`** — `cache/catalog.yaml` (the models.dev catalog), likewise purged by `--purge`. **`ai uninstall` removes all container IMAGES and stops running workspace sessions** so nothing is left on the host: on EVERY uninstall (not only `--purge`) it (1) `stopWorkspaces` — intended to stop every live nono session, but see the "known gap" note above: this step still targets the retired `msb` binary and currently no-ops — and (2) `removeImages` — `rmi -f`s the pinned service-tier images (`versions.Default()`) plus any `aip-*`-tagged image by reference filter (a no-op today since no workspace image is ever built anymore). Because omlx is host-side, a plain uninstall ALSO best-effort stops the running `omlx serve` server and, by DEFAULT, removes the host-native omlx runtime itself (`Options.RemoveRuntimes` defaults to true, `--keep-runtimes` opts out) — the downloaded model store `volumes/models/omlx` SURVIVES a plain uninstall (only `--purge` removes it); `removeOmlx` is currently a documented `hardware bring-up` STUB (reports success but does not actually run a per-OS uninstall). colibri gets its own default-yes prompt (only when installed; `--keep-runtimes` opts out of both): the server is always stopped, and opting in deletes `~/.ai-platform/bin/colibri` (a REAL removal, unlike omlx) while declining preserves it through the state wipe; its models (`volumes/models/colibri`) survive unless `--purge`, which removes everything. A copy installed elsewhere on PATH is reported, never deleted. All state/config writes go through `internal/conffile` (atomic YAML — temp file + rename; reads reject unknown fields via `KnownFields`). `versions.yaml` (`internal/versions`) is the source of truth for the service-tier image refs (image + tag, default `latest`). The `--json` output envelope (`internal/output`) and the in-workspace agent-CLI configs (`<project>/.opencode/opencode.json`) stay JSON. Config merges `project > global` via `internal/config` (deep map-merge).

**The CLI surface is FLAT and smaller than the old microVM-era surface: workspace management lives in top-level verbs** (CLI §3/§4) — `ai create`/`ai list`/`ai delete` (create/list/delete a workspace registration; `ai delete` is the single removal verb, `destroy` is an ALIAS: it stops any live nono sessions, best-effort revokes + removes the OS-keychain credential, then removes the project's `.ai-platform` dir + its `projects.yaml` registration, and — unless `--keep-agent-config` is passed — the per-CLI agent config folders too (their symlinked shared-pool content is materialized to real files first so disabling the symlink doesn't destroy user content); `--purge` additionally removes the whole project directory) and `ai start`/`ai stop`/`ai restart`/`ai shell`/`ai agent`/`ai attach`/`ai sessions` (nono session lifecycle). **`ai mounts`, `ai resize`, and `ai apps` no longer exist** — there is no VM to size, no guest/host mount concept (nono doesn't virtualize the filesystem), and no in-VM container runtime for apps to run on; these were removed outright, not merely deprecated. **`ai start`/`ai stop`/`ai restart` are now sugar over `ai agent`/session management, not VM lifecycle verbs**: `ai start [name]` resolves the workspace's default agent CLI (`config.Agent.DefaultTool`, else the first installed CLI) and either reattaches to its already-running session or launches a fresh one (`attachOrLaunchAgent`); `ai stop [name]` stops every live session for the project (`Manager.StopAll`); `ai restart [name]` stops everything then launches the default CLI fresh. None of them rebuild anything — there is nothing to rebuild; a config.yaml change (e.g. `ai network egress deny`) simply takes effect on the NEXT launch via `ensureProfile`'s per-launch regeneration, no explicit restart required (though restarting is the obvious way to pick it up for an ALREADY-running session, since a live session's profile was fixed at its own launch time). `ai agent <cli> [name]` is the canonical per-CLI launch/reattach verb; `ai shell [name]` opens a bare interactive sandboxed shell with no agent; `ai attach [session] [name]` attaches an existing session by id/name (listing them to pick from with no explicit `[session]`, or hinting at `ai shell`/`ai agent` when there are none to attach to); `ai sessions [name]` lists a project's live nono sessions (ID/NAME/STATUS/ATTACHED/STARTED) and `ai sessions kill <session> [name]` force-stops one. **`ai tools <list|enable|disable> [tool] [name]` (new)** inspects/toggles the ten opt-in AI tools after `ai create` time — `list` shows each tool's enabled state + one-line description from `create.AIToolDescription`; `enable`/`disable` just flip the matching `context.*_enabled` bool in `config.yaml` (`setToolEnabled`) and take effect on the next `ai agent`/`ai shell` launch, since each tool installs/tears down directly on the host at that point rather than anything being baked ahead of time. `ai doctor [name]` always reports platform health + every service-tier service plus host-native omlx, and — when inside a workspace dir (cwd/ancestor) or given `[name]` — a much SIMPLER per-workspace section than the old rootless/virtualization probe: since nono sandboxes a host process directly rather than booting a VM, there is no container-runtime/rootless/virtualization posture to check anymore, just whether `nono` itself is installed (`nono.Detect`) plus the workspace's live nono session count.

**`ai create` is an in-process `charmbracelet/huh` wizard, with a MUCH SMALLER set of groups than the old microVM-era wizard** (CLI §3.1): workspace name + **location** + default interactive shell (bash/zsh) in one group; agent CLIs (multi-select: `opencode`/`omp`/`claude-code`/`codex`/`gemini`/`hermes` — opencode is the default tool) in a second group; default agent CLI in a third; per-agent auth-mode groups for each OAuth-capable CLI actually selected (claude-code/codex/gemini — `api-key`, the default, routes through the gateway with the scoped virtual key and keeps the tool firewall/secret-masking in effect; `oauth` is the CLI's own subscription login, direct to the provider, bypassing the gateway and its guardrails entirely — `ai create` emits a warning for each oauth agent selected); the ten AI tools in ONE multi-select (none selected by default — `create.DefaultAITools()` returns an empty slice, unlike the old design's caveman/graphify-on-by-default); and, ONLY when Graphify is in that selection, a Graphify-model picker built from omlx's live `GET /v1/models` list (a `"(none — leave Graphify unconfigured)"` sentinel always first; a pre-seeded `--graphify-model` value omlx isn't currently serving is appended rather than dropped, so a scripted value still shows for confirmation). **Gone entirely from the wizard**: OS selection (debian-trixie/ubuntu/alma), software stacks (go/rust/java/maven/deno), vCPU/memory/disk sizing, published ports, and in-VM apps — a workspace runs on whatever toolchains the host itself already has; the platform no longer provisions an OS or stack at all. Every remaining input still has a flag (`--name`/`--agents`/`--location`/`--graphify-model`/`--shell`/`--auth-mode`/`--tools`); on a TTY the flags pre-seed the wizard (which always shows), while under `--json`/no-TTY the spec is built straight from the flags with no prompt. The deterministic in-process work — validate the name/location, scaffold `.ai-platform/` (`config.yaml`/`project.yaml`/`.gitignore`), seed context-optimization defaults (Headroom strategy + Caveman level) — lives in the shared `internal/create` package (`create.Execute(spec, now, report)`), imported by both `ai create` and the `ai ui` TUI create wizard so both behave identically. **There is nothing to build and nothing to download at create time** — `create.Execute` finishes in milliseconds, reporting a final step pointing the user at `ai agent <cli>`/`ai shell` to actually start a sandboxed session (the nono profile + per-CLI config are generated lazily on that first launch, not at create). `project.Scaffold` also pre-populates `network.allow_domain` with each selected oauth-mode agent's own provider domains (`agentcfg.OAuthProviderDomains` — claude-code→api.anthropic.com; codex→api.openai.com/chatgpt.com/auth.openai.com; gemini→generativelanguage.googleapis.com/oauth2.googleapis.com/accounts.google.com/cloudcode-pa.googleapis.com) and defaults `network.egress` to `"public"`, so an oauth agent can reach its own provider even if the project is later locked to `deny`. The per-project **AI tools** — caveman, graphify, code-review-graph, codebase-memory-mcp, openviking, tokensave, agentmemory, ponytail, agent-skills (`create.SupportedAITools()`) — each map to a `context.*_enabled` bool in `config.yaml`, installed/torn down on the HOST at `ai agent`/`ai shell` launch time by `internal/workspace/tools.go` (see above), not baked into any Dockerfile snippet (there is no Dockerfile at all anymore).

## Conventions

- **Commands prompt on a TTY** (CLI §1.8), via the shared helpers in `internal/cli/prompt.go` (`interactive`/`runForm`/`promptText`/`promptSecret`/`promptChoice`/`promptMultiChoice`, all built on `charmbracelet/huh`). On a terminal the prompt ALWAYS shows, **pre-seeded** with any value given as an arg/flag (the user confirms/edits — the value never silently bypasses the TUI); only under `--json`/no-TTY is a provided value used directly, with a missing required value erroring (exit 2) so automation stays scriptable. Two exceptions: a **hidden credential value** (`ai keys add --value/--stdin`) is used directly even on a TTY (a hidden field can't show a seed), and `ai services start|stop|restart` act directly on an explicit name/`all` and only show the checkbox with no arg. Known option sets are shown as selects/checkboxes. **All of a command's prompts must share ONE `runForm`** so the user can navigate back between them — never chain separate prompt calls. The TUI look-and-feel is **theme-selectable**: `internal/ui` owns a registry of named themes (huh built-ins `default`/`dracula`/`catppuccin`/`base16`/`monochrome` plus custom palettes in `custom_themes.go` — `orange`/`synthwave`/`cyberpunk`/`tokyo-night`/`nord`/`gruvbox`/`onedark`/…, each wrapping a huh theme + heading accent; `ui.TableStyles()` themes the `ai ui` tables with the active accent), persisted per host in `~/.ai-platform/config/ui.yaml` and applied once at startup (root `PersistentPreRun` → `ui.Apply(ui.LoadThemeName())`); `ai theme [name]` shows/selects it (the semantic status colours stay fixed across themes).
- **No single-character variable names anywhere** — including method receivers and loop vars (`store`, `emitter`, `prober`, `entry`, `value`, …). Self-documenting names over Go's terse-receiver convention. The one kept exception is the test handle `t *testing.T`.
- **Every YAML file the platform generates uses the `.yaml` extension, never `.yml`** — config/runtime/versions/catalog/ui/profile/project state, the `ai services compose` artifact (`~/.ai-platform/docker-compose.yaml`), all of it. The ONLY exception is a filename an EXTERNAL tool mandates: omp reads `~/.omp/agent/models.yml` + `<project>/.omp/config.yml` (documented as `.yml`, not a name we choose), so those stay `.yml`. When a new external tool dictates a `.yml` path, match it and note the exception at the write site; otherwise `.yaml`. (nono's own profile JSON, `nono-profile-<cli>.json`, is JSON by nono's own requirement, not YAML — a separate, intentional exception.)
- **Provider API keys never touch platform disk.** Keys flow straight to the LiteLLM credential store (encrypted at rest by `LITELLM_SALT_KEY`) via `litellm.KeyManager` (`SetCredential`/`DeleteCredential`/`ListCredentials`), which `ai keys` fronts; `ListCredentials` returns names + provider prefixes only (never values), so listings can't leak. `ai keys` is catalog-driven (`internal/catalog`, models.dev): a key is keyed per LiteLLM-routable provider, and `add`/`remove` sync that provider's catalog models into/out of the gateway (`litellm.SyncModels`). It **replaced** the former `ai secrets` command and the `internal/secrets` package.
- **Parallelize with subagents + git worktrees where the work is disjoint — but never at the cost of merge chaos.** When a task decomposes into independent units that touch *different* files, prefer launching multiple subagents in parallel, each in its own git worktree (`isolation: worktree`), then integrate by pulling each branch's files (`git checkout <branch> -- <files>`). Do NOT parallelize units that edit the **same** file (notably `internal/setup/setup_real.go`, `internal/tui/tui.go`) — sequence those instead. The rule that keeps integration clean: each agent owns a **disjoint file set**, and the parent does any shared wiring (e.g. registering new views in `tui.go`) itself. If you can't partition the work into disjoint file sets, do it single-threaded.
- Commit messages must not include AI-attribution trailers (no `Co-Authored-By` for the assistant). Commit only when asked; the work lives on a feature branch off `main`.
